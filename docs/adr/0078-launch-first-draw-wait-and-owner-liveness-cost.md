# ADR 0078: 混んだ端末での起動待ちと、持ち主の生存確認の負荷

状態: 採用。

## 原因

2026-10-03、負荷平均が224〜330（10コア）、総process約1,900のmacOSで2つのことが起きた。

1. `agent_launch`がClaude Code・Cursorで`initial_prompt=not_sent`・`reason=unrecognized_screen`を返した。
   入力受付の待ちは30秒で、切れた時の画面はAitermが打った起動コマンドの表示のままだった。
   15秒後にはTUIが出ていた。agentが何も描く前に待ちが切れている。
2. 動いているaiterm-mcp 18個が`ps -axww`を毎秒約7回呼び、約1.4コア分を使い続けた。
   親配送の管理は、終了した持ち主の記録を引き取る処理を5秒おきに回し、毎回全processの一覧を取っていた。
   1つのMCP processに管理が2つ（手元用と別端末用）ある。`ps`の間はMCPの応答も止まる。

## 判断

### 起動待ちは、TUIが描かれる前だけ延ばす

画面の末尾が起動コマンドの表示のまま30秒を越えた時だけ、起動から50秒まで待つ。
TUIが一度でも描かれた後の画面（見分けられないダイアログを含む）は、今までどおり30秒で返す。

- 見分け方はharnessに依らない。画面の最後の24文字が、Aitermが打った起動コマンドの一部かを見る。
  空白と行頭の継続prompt（`> `／`>> `）は端末の折返しとshellの表示なので比べない。
  shellの表示自体が途中で止まっている画面も、同じ判定で未描画と数える。
- 起動コマンドは`openAgent`が同じprocessの中で控える。stateへは保存しない。起動後の送信では使わない。
- 上限を50秒にしたのは、Codex親の既定のtool timeoutが60秒だからである。`agent_launch`がそれを越えると、
  親には時間切れに見えたまま子へ初手が送られ、未送信・送信済みの区別が親から見えなくなる。
  30秒で`not_sent`を返してsessionを残す今の契約より悪い。待ち時間を呼ぶ側から指定する入力は足さない。
- 50秒でも描かれない時は、今までと同じ`not_sent`と理由を返す。
- 呼ぶ側が既定（30秒）より短い待ちを指定した時は延ばさない。指定した待ちで返す。

### 持ち主の生存確認は、存在の確認と開始時刻の照合に分ける

「pidと開始識別子が同じprocessがあれば生きている」という判定と、記録を引き取る条件は変えない。

- 5秒おきの確認は、closeしていない他の持ち主のpidが今あるかだけを、OSへ直接聞く（`kill(pid, 0)`）。
  processを起動しない。pidが無ければ、開始時刻を照合せずに終了と判定する。
- 開始時刻の照合は、初めて見た持ち主と、その後60秒に1回だけ行う。対象のpidだけを引く
  （POSIXは`ps -o pid=,lstart= -p`、Windowsは`Win32_Process`のfilter）。全processのargvは読まない。
- 確かめる相手が居ない時は、OSへ何も問い合わせない。
- 生死を確かめた後に現れた持ち主は、次の回で扱う。確かめていない持ち主の記録は引き取らない。

対象を絞るだけにしなかったのは、実測で1回の重さがほとんど減らなかったからである
（macOSで全件160ms・対象17個137ms、Windowsで全件171ms・対象1個185ms）。macOSの`ps`は`-p`でも全processを歩く。

### 受け入れる遅れ

持ち主が終了した直後に、同じpidが別のprocessへ再利用された場合だけ、回収が最長60秒遅れる。
生きている持ち主の記録を引き取ることは無い。pidが無くなる通常の終了は、今までどおり5秒以内に回収する。

## 確認

- 画面の描画を33秒遅らせたClaude Codeで、0.47.0は31秒で`unrecognized_screen`、この変更は40秒で初手を送り回答を得た。
  描画しないままの時は51秒で`not_sent`を返した。
- MCP process 3個を40秒動かし、0.47.0は`ps -axww`を60回、この変更は対象を絞った`ps`を14回呼んだ
  （起動時の照合を含む。以後は1 processあたり毎分2回、今までは毎分24回）。
