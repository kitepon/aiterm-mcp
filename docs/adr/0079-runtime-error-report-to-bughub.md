# ADR 0079: 実行時エラーを、明示して有効にした端末からBugHubへ送る

状態: 採用。

## 原因

実行時エラーの記録は、端末のlocal stateに貯めるだけで、Aiterm自身は外へ出さなかった。
工場（dotagents）のreportが読んで運ぶ前提だったが、2026-07-14のwire v2から工場はAitermの分を集めていなかった。
3か月の間、記録は端末にたまるだけで誰にも届かなかった（中身の大半は試験が書いたもので、それも誰も気づかなかった）。

オーナーの裁定（2026-10-03）: エラーを上げるのは各プロダクトの責務。工場は工場の方針と、プロダクト・パッケージの管理だけを持つ。
BugHubは、常駐しないCLIの製品が自分の分を送る受け口を用意した。受けるのはオーナーの端末だけで、家のLANの中にだけ置く。

## 判断

### 既定では通信しない

Aitermはnpmで公開している。外の利用者の端末からは送らない。送るのは、次の2つがそろった端末だけ。

1. 利用者が`aiterm-runtime-errors reporting enable`で明示して有効にした（Aiterm自身の設定。工場の設定は読まない）。
2. BugHubの持ち主が置いた合鍵のファイルがある。

宛先はAitermの中に書かない。合鍵のファイルの`url`から読む。合鍵のファイルは、本人だけが読める通常のファイルだけを読む
（POSIXは所有者と0600、Windowsは既存の私有DACLの検査）。そうでなければ読まずに止まる。

報告を有効にした端末は、記録も有効になる。工場の収集設定が無い端末でも、製品が自分の記録を持てる。
工場の収集設定による記録は、今までどおり動く。

### 送るのは別process、きっかけは出来事だけ

MCP processは通信しない。送信は`runtime-error-worker`の別processが行う。きっかけは次の4つで、タイマーは置かない。

- 実行時エラーを記録した時
- 記録を解決・開き直した時
- MCP processの起動時
- 利用者が`aiterm-runtime-errors report`を実行した時

有効でない端末では、きっかけがあっても何も起動しない（設定ファイルを1つ読むだけ）。
自動の送信は、受け口がまだ受け取っていない記録がある時だけ、多くても1時間に1回。手動は受け口の上限に合わせて1分に1回。
複数のprocessが同時に送らないよう、送信の間は状態の置き場にlockを置く。

定期的な見張りを置かないのは、ADR 0078の教訓による。動いているだけのprocessが、端末の数だけ負荷を足した。

### 受領を確かめた時だけ進める

契約（BugHubの`PRODUCT_REPORTING.md`）に従う。

- 本文は、その時点の累計。契約にある項目だけを載せ、端末名・OS・arch・保存用の連番は送らない。
  prompt・path・stackは保存していないので、送るものが無い。
- 合鍵の秘密は通信に載せない。本文に`HMAC-SHA256(secret, ts + "\n" + 本文のSHA-256)`の署名を付ける。
- 受け取り済み（`acknowledged_cursor`）にするのは、200・`accepted: true`・`report_id`の一致・応答の署名がそろった時だけ。
  家のLANの外で別の機器が200を返しても、受領にしない。
- そろわない時は「届いたか不明」として何も進めない。次の機会に、その時点の累計を新しい`report_id`で送り直す。
  送信待ちの本文は保存しない（回数は累計なので、送り直しで数え過ぎない）。
- 401（時刻のずれを除く）と403は、合鍵が無効と読む。同じ合鍵のファイルのまま、自動では送り続けない。
  合鍵のファイルが置き直されるか、利用者が手で送れば再開する。

### 試験からは送らない

`node:test`の子で動いている時（`NODE_TEST_CONTEXT`がある時）は、自動の送信を起動しない。
CIのrunnerは利用者本人で動く。試験が起動したMCP processが、その端末の本物の記録を、開発中の版の名前で送らないようにする。
試験が利用者の記録へ書いていた件（2026-10-03に直した）と同じ種類の事故を、仕組みで防ぐ。

## 受け入れること

- 解決の印は、直前の送信から1時間以内なら、次のきっかけまで送られない。
- 家のLANの外へ持ち出した端末は、送れない間「届いたか不明」を繰り返す。1時間に1回、10秒で切れる接続を1本試すだけで、端末の動きは変わらない。
- Windowsの合鍵のファイルの検査は、既存の私有DACLの検査に頼る。置き方がこれと違うと、読まずに止まる。

## 確認

- 契約の試験値で、要求の署名と応答の署名が一致した。
- 契約どおりに振る舞う偽の受け口で、有効・無効、合鍵の有無と権限、受領の確認、送り直し、頻度の制限、合鍵が無効な時の扱いを確かめた。
- 本物のprocessで、無効の間は記録しても送らないこと、有効にして記録すると別processが送り、受け取り済みになることを確かめた。
