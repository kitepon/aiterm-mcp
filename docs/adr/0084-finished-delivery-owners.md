# ADR 0084: 終了した配送の持ち主の保存場所を片付け、使い回されたpidの照合を繰り返さない

状態: 採用。ADR 0078の「開始識別子の照合は初めて見たownerと60秒に1回」を、照合の結果が「別のprocess」「照合できない」の時にも及ぼす。
ADR 0080の「起動完了の後に立ったものは数える」から、Aiterm自身の問い合わせを外す。

## 原因

配送の回収（`ParentDeliveryManager.recoverOrphans`）は、MCP processごとに5秒おきに回る。持ち主の保存場所
（`…parent-deliveries/active/<持ち主>/owner.json`）を全部読み、closeしていない持ち主のpidが居れば、開始時刻をOSへ問い合わせる。

- 終了した持ち主の保存場所は、記録を引き取った後も消していなかった。MCP processはほとんどの場合closeを書かずに終わるので、
  `closed:false`のまま溜まる。
- 開始時刻が同じと分かった結果だけを60秒覚えていた。別のprocessと分かった結果は覚えず、5秒おきに問い合わせ直していた。
- OSがそのpidを別のprocessへ使い回すと、その持ち主は「pidは居る」ので、永久に問い合わせの相手になる。

実物（2026-10-04、Aiterm 0.51.1）:

- Windows 11の端末。保存場所は6つの置き場で約1,620、`closed:true`は0、pidが居るものが56（chrome・svchost・WidgetServiceなどへの使い回し）。
  長く動いているMCP process 4つが、それぞれ約2.7秒に1回PowerShellを起こしていた（85秒で約260回。回収は手元用と別端末用の2つ）。
- macOSの端末。`parent-deliveries`に829、使い回しは5。同じ問い合わせは`/bin/ps`になる。
- Linuxの端末は使い回しが0で、問い合わせは起きていなかった。
- Windowsでは、席の`activity.post_startup_process_count`が0と2を行き来した。席の中のAitermが起こすPowerShellと、
  付いて立つconsole hostを、起動完了の後に増えたprocessとして数えていた（4秒おきの21回中、Cursor 2回・Claude Code 4回）。
- Windowsの開始時刻の照会は、CommandLineを読めないprocessを結果から落としていた。pidが権限の違うserviceへ使い回されると、
  行が返らず、「別のprocess」と確かめられない。

## 判断

### 終了した持ち主の保存場所を消す

記録を引き取り終えた後、次の保存場所を消す。

- 持ち主が自分で閉じたもの（`closed:true`で、`closed_reason`が無い）。
- closeしていなくて、pidがもう無いもの。
- 回収側が閉じたもの（下）で、そのpidがもう無いもの。
- `owner.json`が無く、60秒より古く、空のもの。

引き取りの判定は変えない。引き取る条件（閉じた・pidが無い・開始時刻が違う・照合できない）は今までと同じ。

### 使い回されたpidの持ち主は、回収側が閉じる

pidは居るが開始時刻が違うと確かめた持ち主は、`owner.json`を`closed:true`・`closed_reason:"pid_reused"`へ書き換える。
同じpidと開始時刻の組は二度と現れないので、閉じて差し支えない。`closed`の持ち主は、どの版の回収も生存を確かめない。
この版より前のMCP processが同じ端末で動いていても、その持ち主への問い合わせは止まる。

この保存場所は、そのpidを別のprocessが使っている間は残す。消すのは、pidが無いという確かな事実がある時だけにした。
開始時刻の文字列は、POSIXでは`ps`が現地時刻で返す。持ち主と回収側でTZが違うと、生きている持ち主を「別のprocess」と読む。
その取り違えは今までも記録の引き取りを起こしていたが、保存場所を消すところまでは広げない。

書き換えに失敗した時は、何もせず次の回でもう一度照合する。配送には影響しない。

### 照合できない持ち主は、60秒に1回だけ問い合わせる

pidは居るのにOSが行を返さない持ち主（照会の直前に終了した、開始時刻を読めない）は、今までどおり記録を引き取る。
結果を覚え、次の照合は60秒後にする。閉じた事にはせず、保存場所も消さない。

Windowsの開始時刻の照会から、CommandLineの条件を外す。使い回された先がserviceでも行が返り、「別のprocess」と確かめられる。

### 旧版の持ち主が生きている間は消さない

この版より前の回収は、`owner.json`を読んだ後に保存場所の一覧を取る。その間に保存場所が消えるとENOENTで回収が失敗し、
`PARENT_DELIVERY_STATE_UNAVAILABLE`がそのMCP processに立ったままになる（以後の`agent_launch`が失敗する）。

- 持ち主は`owner.json`へ`removal_safe:true`を書く。保存場所が消えても読める版の印。
- 同じ置き場に、この印の無い持ち主が生きている（closeしていなくて、終了を確かめられない）間は、何も消さない。
- `owner.json`がまだ無い新しい保存場所（60秒以内）も、版が分からないので同じ扱いにする。
- 読む側（回収、記録の一覧）は、一覧を取った後に保存場所が消えていても、その保存場所を飛ばす。

旧版が居る端末では、片付けは旧版のMCP processが全部終わった後の回で起きる。使い回されたpidを閉じる処理は、旧版が居ても行う
（`owner.json`の置き換えは原子的で、旧版は`closed`の持ち主を今までどおり読む）。

親の種類が違う置き場（`parent-deliveries`と`claude-parent-deliveries`など）の旧版は、記録の一覧（`status`、送信前の確認）だけが
ほかの置き場を読む。一覧の途中で保存場所が消えると、その1回のtool呼び出しがENOENTで失敗する。立ったままにはならない。
起きるのは片付けと一覧が同じ瞬間に重なった時だけなので、ここは防いでいない。

片付けに失敗した保存場所は残し、次の回でもう一度消す。失敗を配送の異常にはしない。

### Aiterm自身の問い合わせを、席のprocessとして数えない

`activity.post_startup_process_count`から、次を外す。

- Aitermがprocess表を引くために起こしたprocess。コマンドの形で見分ける（POSIXは`/bin/ps`の2つの引数の並び、
  WindowsはPowerShellの`-EncodedCommand`の先頭2行）。形は起こす側と同じ定数から作る。
- Windowsのconsole hostのうち、親がその問い合わせのもの。親が先に終わって残ったものも外す。console hostは最後のconsole processと
  一緒に消えるので、利用者の作業に付いたconsole hostは、その作業のprocessが別に数えられる。

回収の問い合わせ自体は、生きている他の持ち主が居る限り60秒に1回は残る。数える側で外さないと、その瞬間に0でなくなる。

## 採らなかった案

- 終了と分かった結果をMCP processの中だけで覚える。この版より前のMCP processの問い合わせは止まらず、保存場所も減らない。
- 旧版が居ても消す。上の通り、旧版の配送が止まる。
- `ps`の開始時刻をUTCで取る。持ち主が記録した開始時刻と、保存場所の名前（開始時刻のhash）の両方が変わり、
  版をまたいだ照合が合わなくなる。

## 影響

- `owner.json`に`removal_safe`と`closed_reason`が増える。`pid`・`started_identity`・`closed`は変えない。旧版はこの2つを読まない。
- 新しい版のMCP processが1つ起きると、その置き場の使い回されたpidは最初の回収で閉じられ、同じ端末の旧版も問い合わせなくなる。
- `aiterm.pty-observe-result.v1`の形は変えない。
- `close()`は2回呼ばれても2回目は何もしない（閉じた後の保存場所は、記録を引き取った側が消す）。
