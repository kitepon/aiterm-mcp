# ADR 0085: 完了待ちの中で画面を読む間隔を、完了の見回りから分ける

状態: 採用。

## 原因

完了待ち（`observeAgentDone`と、Cursor・Grokの同じloop）は100msごとに回る。完了の判定は、event fileや記録のstatと増分読みで軽い。
同じ周回で、利用上限の知らせを毎回画面から確かめていた（Claude・Cursor・Grok）。画面を読むたびに`tmux capture-pane`を1回起動する。
Cursorは利用上限とhook拒否の表示を別々に読み、1周で2回起動していた。Codexは記録で見分けるので、画面を読まない。

実物（2026-10-04、Aiterm 0.51.1、Linux）:

- 待ち1本（Claude Codeの子）で、8秒間にtmuxの起動が76回。待ちが4本重なった時は8秒間に400回で、BellTeamのコンテナのCPUが148%だった。
- 手元で同じ数え方（`AITERM_TMUX`へ引数を記録するscriptを渡す）: Claude Codeの子で8秒に75回、Cursorの子で142回。

## 判断

画面を読む間隔を、完了の見回りと別に持つ。

- 利用上限の知らせ（Claude・Grok）は2秒に1回。
- Cursorは1秒に1回読み、その1回の画面で利用上限とhook拒否の両方を見る。hook拒否の表示は数秒で消えるので、見えている間に1回は読む間隔にした。
- 待ちに入った最初の周回では必ず読む。`timeout=0`の照会も1回は読む。
- 完了の見回り（100ms）は変えない。完了が届く速さは同じ。

読む時刻が今までの一部になるだけで、何を上限と読むかは変えない。今の画面だけを見る（終わった上限の知らせをpane logから拾わない）作りはそのまま。

変わるのは、子が利用上限で止まった時に`rate_limited`を返すまでの時間で、最長でClaude・Grokが2秒、Cursorが1秒遅れる。

直した版の実物: 待ち1本・8秒間で、Claude Codeの子が4回、Cursorの子が8回。

## 採らなかった案

- 完了の見回りを遅くする。完了が届くのが遅れる。
- 画面を読まずに上限を見分ける。ClaudeとCursorは、上限で止まった事を記録へ書かない（画面にしか出ない）。

## 影響

- `aiterm.agent-wait-result.v1`の形は変えない。
- `pty_observe`・`pty_list`は、呼ばれた回ごとにtmuxを起動する（`pty_observe`は3回）。ここは変えていない。回数は呼ぶ側で決まる。
