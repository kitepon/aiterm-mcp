# ADR 0086: pidは居ると出るがprocess表に無い持ち主を、終了として閉じる

状態: 採用。ADR 0084の「照合できない持ち主は、60秒に1回だけ問い合わせる」を、開始時刻を読めない持ち主だけに狭める。

## 原因

ADR 0084は、pidは居るのにOSが行を返さない持ち主を「照合できない」として、閉じずに60秒ごとに問い合わせ直していた。

実物（2026-10-04、Windows 11、0.51.2へ更新した後）で、この版より前のMCP process 3つが、1分に22〜24回の問い合わせを続けていた。
聞いているpidは6つで、どれも次の状態だった。

- 権限を上げていないnodeでは`process.kill(pid, 0)`がEPERM。Aitermはこれを「居る」と読む。
- 権限を上げたnodeではESRCH。`Win32_Process`には載らない。
- 終了したprocessのpidが、誰かがhandleを握っている間は空かずに残っている。

0.51.2は、この持ち主を60秒に1回へ減らすが、`closed`にはしない。前の版の回収は、5秒ごとに問い合わせ続ける。

## 判断

closeしていない持ち主を照会した結果を、次の4つに分ける。

- 開始時刻が同じ: 生きている。
- 開始時刻が違う: pidは別のprocess。閉じる（`closed_reason:"pid_reused"`、ADR 0084）。
- process表にそのpidが無い: 終了している。閉じる（`closed_reason:"process_gone"`）。
- process表にはあるが、開始時刻を読めない: 照合できない。閉じずに、60秒に1回だけ問い合わせる。

process表に無いpidは、生きているprocessではない。pidが居ると出てから照会までの間に終了したか、終了したprocessの名残のどちらか。
POSIXの`ps -p`も、WindowsのWin32_Processも、生きているprocessは必ず返す。

閉じた保存場所を消すのは、ADR 0084と同じく、そのpidが無くなった時。名残のpidは、握っているprocessが終わるか再起動するまで残る。
権限を上げたMCP processからは「pidが無い」と見えるので、そちらが先に消す事がある（旧版が居ない置き場に限る）。

Windowsの開始時刻の照会は、開始時刻を読めない行も返す（`started_identity`はnull）。pidがprocess表にある事と、無い事を区別するため。

## 影響

- `closed_reason`に`process_gone`が増える。0.51.2は`closed_reason`の値を見ず、有無だけを見るので、0.51.2と混ざっても同じに動く。
- 新しい版のMCP processが1つ起きると、その置き場の名残のpidの持ち主は最初の回収で閉じられ、前の版も問い合わせなくなる。
