# ADR 0094: Claude親への配送の置き場は、届いたら消し、届かなかった分は1日残して消す

状態: 採用。

## 原因

Claude Code親への配送は、道具の呼び出し1回につき置き場を1つ作る（Aiterm stateの
`claude-parent-hooks/<tool_use_id>/`）。`PreToolUse`のhookが親の記録（`request.json`）を置き、Aitermが配送を結び
（`delivery.json`）、子の回答（`answer.json`）を置き、`PostToolUse`のhookが本文を出して記録（`hook.json`・
`sending.json`・`emitted.json`）を残す。

この置き場を消していたのは1か所だけだった。`PostToolUse`のhookが、配送を結んでいない呼び出し（通常のPTYなど）を
見た時である。配送のある呼び出しは、届いた後も置き場が残った。届いた子1つにつき1つ増える。

- 連携元（BellTeam）の本番で、届いた配送3件の置き場が3つ残っているのを見た（2026-10-06、0.55.0）。
- 道具の返りが誤りの時、Claude Codeは`PostToolUse`を走らせない（ADR 0093）。この呼び出しは`request.json`だけの
  置き場を残す。Claude側で打ち切られた呼び出し（時間切れ、利用者の中断）も同じ。
- 置き場はOSの一時置き場にある。LinuxとMacは再起動で消えるが、Windowsは消えない。Windowsの試験端末には
  18日前の置き場が残っていた（届いた4つと、`request.json`だけの4つ）。
- 会話終了のhookは、置き場を全部見回って`request.json`を厳密に読み、1つでも読めないと例外で止まった。
  記録の形を変えると、古い残りでこの見回りが止まる作りだった。

今の数（端末ごとに3〜8）では害は出ていない。放っておくと、長く動く端末で増え続ける。

## 判断

置き場の持ち主は、依頼元のClaude processと、その依頼に結んだ1件の配送である。配送が届けば置き場の役目は終わる。
片付けは共通パッケージ（`aiterm-steer-delivery` 0.2.2）に置く。Aitermは依存を`^0.2.2`へ上げる。

### 届いた置き場は、送り手が消す

`submitClaudeParentAnswer`は、受信hookが本文を出し終えた記録（`emitted.json`）を確かめた後に、置き場ごと消す。
この後に置き場を読む物は無い（配送の結果はAitermの配送記録に`submitted`として残る）。

- 消せなかった時も、配送は成功のまま返す。片付けの失敗を配送の失敗にしない。
- 届かなかった時（誤りで返す時）は消さない。0.54.0で回答が届かなかった件（ADR 0093）は、残った`request.json`・
  `delivery.json`・`answer.json`と、`hook.json`が無い事から原因が分かった。

### 届かないまま残った置き場は、1日残してから、次の依頼のhookが消す

`PreToolUse`のhookは、親の記録を置いた後に置き場を見回る。消すのは、次の両方に当たる置き場だけ。

- 最後に書かれてから1日たっている（置き場と、中のfileの更新時刻のうち新しい方で測る）。
- 待っている配送が無い。次のどれかに当たる: 配送を結んでいない、依頼元のClaude processが居ない（pidが無いか、
  同じpidの別のprocess）、出し終えている、依頼元の記録を読めない。

依頼元が居て、配送を結んであり、まだ出し終えていない置き場は、何日たっても残す（子が長く動いている配送）。
この製品の依頼の記録でないfileが入ったdirectoryには触れない。見回りの失敗では依頼を止めない。

- 1日は、届かなかった時に原因を調べる間である。配送の記録（`parent_deliveries`）は別に残る。
- hookは親を記録するためにprocess表を1回読んでいる。見回りはその表を使うので、読む回数は増えない。

### 会話終了の見回りは、読めない記録で止まらない

`closeClaudeParentSession`は、読めない`request.json`と、消えている途中の置き場を飛ばして続ける。送り手と見回りが
置き場を消すようになったので、見回りの途中で置き場が消える事がある。

## 退けた案

- **会話終了のhookで消す**: 会話終了のhookは短い時間で打ち切られ、process表を読む余裕が無い（Windowsは約1秒かかる）。
  `/clear`でも会話は終わるが、依頼元のprocessは続き、結んだ配送は「会話が終わった」と断るために置き場を読む。
- **Aitermの回収処理（常駐するMCP process）で消す**: 置き場は共通パッケージの物で、同じパッケージを使う他の製品も
  同じ残りを持つ。hookは全ての製品で必ず走る。
- **届かなかった置き場も、すぐ消す**: 原因を調べる材料が無くなる。
- **届いた置き場も、1日残す**: 届いた配送の置き場には、配送の記録より多い情報が無い。数が増える元は届いた配送である。

## 影響

- 届いた配送の置き場は残らない。置き場に残るのは、届かなかった依頼（最長で依頼元が終わってから1日。依頼元が
  居て配送を待っている間はずっと）と、配送を結ばなかった依頼（1日）である。
- 0.55.0以前が残した置き場は、0.55.1のhookが最初に走った時に、上の決まりで消える。
- 依頼元のClaude processが居なくなってから1日より後に子が終わった配送は、置き場が消えているので、
  `CLAUDE_PARENT_PROCESS_CLOSED`でなく`CLAUDE_PARENT_HOOK_UNAVAILABLE`で失敗する。どちらも届けていない。
  OSの再起動で一時置き場が消えた後と同じ形である。
- 道具の返り、配送の記録の形、hookの登録は変わらない。setupの流し直しは要らない。

## 確かめ

- 共通パッケージの試験（3つのOS、GitHubの`ubuntu-latest`・`macos-latest`・`windows-latest`、各62件で失敗0）:
  届いた依頼の置き場が消える事。届かなかった依頼（受信hookが先に居なくなった、会話が終わっていた）の置き場と
  回答が残る事。置き場を消せなくても配送が成功で返る事（POSIX）。会話終了の見回りが、形の違う記録・壊れた記録・
  空の置き場を飛ばして、その会話の依頼を閉じる事。見回りが、消す置き場（配送を結んでいない、依頼元が居ない、
  pidが使い回されている、出し終えている、依頼元を読めない、消している途中）と、残す置き場（1日たっていない、
  依頼元が居て配送を待っている、中に新しい書き込みがある、この製品の記録でないfileがある）を分ける事。
- Aitermの試験: 届いた依頼の置き場が残らず、届かなかった依頼の回答が残る事（`test/claude-parent-receiver.test.mjs`）。
- 実物の親子（Claude Code 2.1.291の親、Claude Codeの子、専用の置き場、npmの`aiterm-steer-delivery` 0.2.2）:
  置き場へ残りの見本を5つ置いてから走らせた。回答は親へ届き、配送は`submitted`。届いた依頼の置き場は消えた。
  2日前の見本3つ（配送を結んでいない、形の違う記録、配送を結んだまま依頼元が居ない）は消え、残す見本2つ
  （依頼元が居ないが今日の物、依頼元が居て配送を待っている30日前の物）は残った。
- 3つのOSの実物（公開前。親のAitermだけを直した版へ向け、hookは端末に入っている0.55.0のまま）:
  rabbit（Linux、Claude Code 2.1.291）・macbook（Mac、2.1.289）・fox（Windows、2.1.291）の3台とも、手すきの親と
  作業中の親の両方へ回答が届いた。届いた2件の置き場は増えなかった（rabbit 5→5、fox 8→8、macbook 3→4）。
  macbookで増えた1つは、試験の道具が親を閉じた時に打ち切られた呼び出しの物（`request.json`と`closed.json`だけ）。

## 見ていない事

- hookの見回りを、MacとWindowsの実物のClaude Codeから走らせる事（公開前の3台の確かめは、hookが0.55.0のまま）。
  公開の後、3台を更新してから、古い残りが消える事を現地で確かめる。
- 依頼元のClaude processが居なくなってから1日より後に、子が終わる配送の実物。
- 置き場が数百ある時の、見回りにかかる時間。1つにつき、更新時刻を読むのが1回である。
