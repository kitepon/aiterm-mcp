# ADR 0095: 会話欄の「esc to interrupt」を、Claude CodeとCodexの動作中の印にしない

状態: 採用。

## 原因

`claudeTuiBusy`（`src/harnesses/claude.ts`）は、画面の末尾32行のどこかに`esc to interrupt`の語があれば、Claude Codeを
動作中と読んでいた。この語はClaude Codeが動いている間に足元の行へ出す印だが、会話欄（回答、依頼文、道具の出力）や、
入力欄へ打ちかけの文にも書ける。

- 回答か依頼文にこの語がある席は、turnが終わった後も`pty_observe`が`busy`を返し続けた。次のturnで語が末尾32行の外へ
  流れるまで変わらない。Aitermの中身を話している席で起きる。連携元（BellTeam）は、`idle`が続いた席を閉じる判定に
  `pty_observe`を使うので、その席は閉じない。
- 起動時promptにこの語があると、promptが入力欄へ入った時点（送る前）で`busy`と読んだ。起動時promptの開始の確認
  （ADR 0093）は`busy`を開始の印にする。

ADR 0093で「別の弱さなので混ぜない」と残した件である。

Codexにも同じ読み方があった。`codexPaneObservation`（`src/harnesses/codex.ts`）は末尾24行、送信の前に見る
`isAgentTuiBusy`（`src/core.ts`）は末尾45行のどこかにこの語があれば、動作中と読んでいた。Codexは送信の道でも
この読みを使うので、害が大きい。

- 回答にこの語が残ったCodexの席（0.160.1の実物）は、turnが終わった後も`pty_observe`が`busy`を返し続けた。
- その席への次の`pty_send`は、差し込み（`agent_steer`）として返った。「完了は元の依頼への通知として1回だけ届く」と
  案内するが、元の依頼は既に終わっている。Codexは文を受け取って新しいturnとして答えたが、呼び出し側には
  完了待ちの手段（`wait_process`・`event_cursor`）も、親への配送も渡らなかった。

## 判断

動作中の印として数えるのは、Claude Codeが自分で出す行だけにする（`claudeInterruptHint`）。入力欄（すぐ上が罫線の`❯`行）を
見つけた時は、次の行にある語だけを数える。

- 入力欄の下の罫線より後（足元の行）。
- 入力欄より上の、会話欄と見分けられない行。会話欄の行は、回答の印（`●`。macOSは`⏺`）か依頼文の印（`❯`・`>`）で
  始まるか、字下げされている。古い版の進行行（`✻ Musing… (esc to interrupt)`）は行頭から始まるので、今までどおり数える。

入力欄の中（打ちかけの文と、その続きの行）は数えない。入力欄の無い画面は、今までどおり末尾のどこにあっても数える。
進行行での判定（`claudeTurnProgress`、ADR 0093）は変えない。

見分けられない行を数える側へ倒すのは、動いている席を入力待ちと読む方が害が大きいからである（入力待ちが続いた席は
閉じられる）。

### Codex

Codexは動いている間、入力欄の上へ`◦ Working (5s • esc to interrupt)`の行を出す。見出しの文（`Working`）は作業の内容で
変わるが、括弧の中の形（経過時間、`•`、語）は変わらない。動作中の印として数えるのは、この形だけにする（`codexTuiBusy`）。
`codexPaneObservation`と`isAgentTuiBusy`の両方で使う。

- Codexは、動作中の行と回答の行が同じ印（`•`）で始まる。Claudeのように行頭の印では見分けられない。
- 位置（入力欄のすぐ上）では絞らない。動作中の行と入力欄の間には、待ち行列の文などが入る。

## 退けた案

- **進行行の形（行頭の回る記号）に合う行だけを数える**: 知らない記号の版で、動いている席を入力待ちと読む恐れがある。
- **足元の行だけを見る**: 足元にこの語を出さない古い版は、進行行の括弧の中に出す。

## 影響

- 会話欄か入力欄にこの語があるだけのClaude Codeは、`pty_observe`が`idle`を返す。
- 動いている間の読みは変わらない。
- 会話欄にこの語があるだけのCodexは、`pty_observe`が`idle`を返し、次の`pty_send`は新しいturn（`agent_dispatch`）になる。
- Codexの会話欄に、動作中の行そのもの（`(5s • esc to interrupt)`の形）の写しがある時は、今までどおり動作中と読む。
- Codex（0.160.1）は、回答を流している間、動作中の行を出さない。その間は、この変更の前も後も`idle`と読む
  （会話欄に語があった席だけ、前は偶然`busy`と読んでいた）。この弱さは別の件で、この変更では直していない。

## 確かめ

- 試験（`test/harness-pane-observation.test.mjs`）: 回答・回答の続き・依頼文・道具の出力・macOSの回答の印・打ちかけの文に
  語がある画面を`idle`と読む事。足元の行、古い版の進行行、入力欄の無い画面は今までどおり`busy`と読む事。
- 実画面の通し（Claude Code 2.1.291、0.55.0の判定と直した版の判定）: 前に採った3つの形（1行・複数行・作業の一覧）の
  251場面は、読みが1つも変わらない。依頼文と回答に語を入れた形の63場面は、動いている59場面が`busy`のまま、
  2場面が`busy`から`idle`へ変わった（promptが入力欄にあって送る前の1場面と、turnが終わった後の1場面）。
- 3つのOSの実物（現地は0.55.1、手元は直した版。`remote`付きで現地のClaude Codeの子を、語を入れたpromptで起こした）:
  rabbit（Linux、2.1.291）・macbook（Mac、2.1.289）・fox（Windows、2.1.291）の3台とも、動いている間は手元も現地も
  `busy`、終わった後は手元の判定が`idle`、現地の`pty_observe`は`busy`のままだった。macOSの回答の印が`⏺`である事は、
  この確かめで分かった（最初の版はmacbookだけ`busy`のままだった）。

- Codexの試験: 0.160.1の実画面の形で、回答と依頼文に語がある止まった画面を`idle`と読む事。経過時間の無い括弧
  （`(esc to interrupt)`）を印にしない事。動いている間の行（見出しの文と後ろの知らせが違う5つの形）を`busy`と読む事。
- Codexの実物（0.160.1、専用の置き場）: 直す前は、語のある回答の後に`pty_observe`が`busy`、次の`pty_send`が
  `agent_steer`で完了待ちの手段なし。直した版は、`idle`、`agent_dispatch`、完了が`done`で届き、回答も読めた。
  語の無い普通のturnは、直す前と同じ。
- Codexの実画面の通し（3回分139場面、0.55.0の判定と直した版の判定）: 語の無いturnの45場面は読みが変わらない。
  語のあるturnで`busy`から`idle`へ変わった16場面は、promptが入力欄にあって送る前、回答を流している間
  （動作中の行が出ていない）、turnが終わった後の3つの形だけ。動作中の行が出ている場面は全部`busy`のまま。
- Codexの別端末の実物（現地は0.55.1、手元は直した版）: 終わった後の画面を、手元の判定は`idle`、現地の`pty_observe`は
  `busy`と読んだ。rabbit（Linux）・macbook（Mac）・fox（Windows）の3台とも同じ。

## 見ていない事

- Codexの0.160.1より前の版の実画面。括弧の中の形は、前に採った試験の見本（`(2m 18s • esc to interrupt)`など）と同じ。
- Codexが回答を流している間に`pty_send`した時、何が起きるか。

- 2.1.289より前のClaude Codeの実画面。古い版の進行行は、試験の見本（括弧の中に語がある形）だけで見ている。
- 回答の印が`●`・`⏺`以外になる環境。その時は今までどおり`busy`と読む。
