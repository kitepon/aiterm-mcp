# ADR 0101: Codexが回答を流している間に届いた文を、差し込みとして返す

状態: 採用。

## 原因

Codex（0.160.1）は、回答を流している間、画面に動作中の行（`esc to interrupt`）を出さない。途中の一言を流している間も、最後の回答を
流している間も同じで、長い回答なら何十秒も続く。Aitermは画面で振り分けるので、その間の席を「入力待ち」と読み、届いた文を新しいturn
（`mode: agent_dispatch`、`event_cursor`と完了待ちつき）として返していた。

Codex自身は、その文を動いているturnへ取り込む（turnは1つのまま）。実物で、400行の回答を流している間に送った2通目は、
1通目と同じturnで終わり、回答は「400行＋1通目の印＋2通目の答え」の1つだった。

- 害: 返りが差し込みでなく新しいturnになる。同じ1つの回答が2回の完了として届く（親への配送があれば2通）。
- 新しいturnの道は、入力受付の確かめ（0.5秒おきに11回）を通るので、受け付けを返すまで5.6秒かかっていた。

## 決めた事

Codexの席への送信の振り分けで、画面は入力待ちに見えるが、記録（rollout）の上でturnが動いている席を、動いていると数えて
差し込み（`mode: agent_steer`）で返す。

止まっている席を動いていると読むと、文は新しいturnになるのに差し込みとして返り、その完了を誰も待たない（連携元では、答えが画面に
出ない）。読み違えない方へ倒し、次を全部満たす時だけ動いていると数える。1つでも欠けたら、今までどおり新しいturnの道へ回す。

1. 画面に入力欄が見えている（`composer_ready`）。承認などの画面は、新しいturnの道が今までどおり打鍵前に断る。
2. この起動の記録の、末尾から見て最初の境界が、turnの開始（`task_started`）。記録は、起動の印（launch_id）か、結び付けた
   sessionで決める。記録が無い、結び付かない、書いている途中、境界が読む範囲に無い時は、動いていると数えない。
3. 席のCodexのprocessが生きている。
4. 0.4秒おいて見直しても、記録は同じturnの開始のままで、画面が動いている。見直す間に動作中の行が出た時は、画面の読みでも動いている。

2と3の根拠: Codexは、processが生きている間、turnの終わりを必ず記録へ書く。終わりを書かないのは、落ちた時だけ。
4は、それでも記録が開始のまま残る場面（見ていない終わり方、終わりの書き込みの遅れ）に備えた、記録と別の裏付け。
回答を流している画面は約0.15秒ごとに動き、止まっている席の画面は動かない。

`pty_send`の引数、返りの形、断りの文面は変えない。Claude Code・Grok・Cursorの席、画面に動作中の行が出ている時の動きも変えない。

## 取らなかった形

- **記録だけで決める（2と3だけ）。** 記録の読みが1つ外れると、その席への送信が全部差し込みになる。害は「回答が2回届く」より重い。
- **終わるまで待ってから新しいturnで送る。** Codexは届いた文をその場で取り込むので、待つ意味が無い。待つ間、送信の順番も塞ぐ。
- **画面の読みを直す。** 回答を流している間、動作中を示す決まった行が画面に無い（足元の回る記号は、出る時と出ない時がある）。

## 及ばない所

- 回答の流れが0.4秒より長く止まった所へ届いた文は、今までどおり新しいturnとして返る（同じ回答が2回届く）。
- turnの終わり際（送る時は動いていて、文が着く前に終わる）の競合は、画面の読みで振り分ける時と同じく残る。
- 席へ手で`/new`・`/clear`を打って新しい会話へ切り替えた後は、Aitermが最初の会話の記録を見続ける（この決定より前から）。
  その後の文は今までどおり新しいturnで返り、完了は拾えない。
  → ADR 0105で直した（今の会話の記録を読む）。
- 手で打った`/compact`の途中は、画面に動作中の行が出るので、この決定より前から差し込みで返る。Codexはその文を、圧縮の後に
  新しいturnとして流す。

## 確かめ

- `test/codex-running-by-record.test.mjs`: 記録の読み（開始・終わり・誤りつきの終わり・止めた時・別の起動の記録・書いている途中）。
  回答を流す画面をまねる偽の席と手で書いた記録で、差し込みで返る事、画面が動いていない席・記録の上で終わっている席・
  前の起動の切られた記録しか無い席・見直す間に終わりが届いた席は新しいturnで返る事。
- 実物のCodex（0.160.1、画面つきの席）を偽のmodelにつないで、止まっている席を読み違えない事:
  Escで止めた番とC-cで止めた番は`turn_aborted`（`interrupted`）、HTTP 500・HTTP 401・利用上限（429）・途中で切れる応答は
  どれも`task_complete`（誤りつき）を記録へ書き、次の文は新しいturnで返って完了まで届いた。番の途中で合図なしに止めて記録を
  `task_started`のまま残し、同じ名前で起こし直した席も、新しいturnで返って完了まで届いた。番の途中の`/new`・`/clear`はCodexが
  断り、止まっている所で切り替えた後の文は新しいturnで返った。止まっている席の画面は、12回見て1度も動かなかった。
- 実物のmodel（Linux・macOS・Windows、Codex 0.160.1）: 400行の回答を流している間に送った2通目は`agent_steer`で返り
  （受け付けまで、LinuxとmacOSは約0.8秒、Windowsは約2秒。Windowsはprocessの一覧を引く分だけ遅い）、回答は1つのturnに
  「400行＋1通目の印＋2通目の答え」。Linuxでは、完了が1回だけ届く事も見た。
- 見ていない物: ChatGPTのログインそのものが外れている間に届いた文（見たのは、APIが401を返す形まで）。
