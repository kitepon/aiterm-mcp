# ADR 0105: Codexの席で会話が切り替わった後も、今の会話の記録を読む

状態: 採用。

## 原因

Codex（0.160.1）は、入力欄の`/new`・`/clear`で、processを生かしたまま新しい会話へ移る。実物（公式のCodexと手元の偽のmodel、2026-10-08）で見た形:

- 新しい会話は、別の記録（rollout、別の会話ID）へ書かれる。新しい記録は、命令を打った時ではなく、最初のturnで出来る。
- 古い記録には、切り替えの時に何も書かれない（末尾も更新時刻も変わらない）。
- 新しい記録も、頭のdeveloperの文に、同じ起動の印（`AITERM_AGENT_LAUNCH_ID`）を持つ。印は起動時に渡した指示から来る。
- turnの途中の`/new`・`/clear`は、Codexが断る。

Aitermは、最初の会話のID（`vendor_session_id`）で記録を決め、その後も同じ記録を見続けていた。切り替えた後のturnは、
完了待ちが完了を拾えずに時間切れになり、回答の読み出しは前の会話の回答を返し、送信の振り分けは前の会話の境界を読んでいた。
席を閉じるまで直らない。

BellTeamは席へ命令を打たないので当たらない（トロニー氏の確かめ、2026-10-08: 246回の起動で、1つの印に記録は必ず1本）。
当たるのは、人やほかの席が、Aitermの席の画面へ命令を直接打った時。

## 決めた事

1. Codexの席の「今の会話の記録」（`codexRootTranscript`）は、結び付けた会話の記録か、それより後に書かれた、この席の新しい会話の記録。
   新しい会話と数えるのは、次を全部満たす記録だけ。複数あれば、最後に書かれた物。
   - 会話IDがUUIDv7で、その作成時刻が、この席の起動より後。
   - 結び付けた会話の記録より後に書かれている（更新時刻）。
   - Codex CLIのroot会話（`originator`が`codex-tui`、`source`が`cli`）で、developerの文にこの起動の印がある。
   - ほかの会話から派生した会話（`session_meta`の`forked_from_id`）でない。
2. 派生を追わない理由: 派生は元の会話の文を写すので、印だけでは、どのprocessの会話か決められない。別の端末で派生させた会話を
   拾うと、席の会話でない記録の完了を返す。派生でない会話が印を持つなら、その印を渡されたprocess（この席）が始めた会話。
3. 結び付け直すのは、席の持ち主だけ（送信の道の`bindCodexTranscriptSession`。新しいturnを送る時に`vendor_session_id`を書き換える）。
   完了待ちは、今までどおり席の登録を書かない。
4. 完了待ち（`observeCodexDone`）は、読み位置（cursor）が指す、結び付けた会話の記録から読み始める。待ち始めてから3秒おきに、
   その記録が1行も増えていなければ、今の会話の記録を見直す。別の記録へ移っていたら、そちらを読む。
   - 読み位置つきで待っている時（送信の後の待ち）: 送る時に無かった会話なので、前の会話の最後の書き込みより後の完了だけを数える。
   - 読み位置なしで待ち始めた時: 今までどおり、今より後の完了を待つ。
   - 普通のturnは、送った文がすぐ記録へ書かれるので、ここへ来ない。
5. 回答の読み出し（`codexTranscriptText`）と、送信の振り分けが読む境界（`codexTurnSettled`・`codexRunningTurn`）も、今の会話の記録から読む。
6. 記録がこの起動の会話かの判定は、起動ごとにprocessの中で控える（頭の読み直しを避ける）。書いている途中で決められない記録は控えない。
7. 変えない物: 引数、返りの形、断りの文面、席の登録の項目、会話が切り替わっていない席の読み。
   切り替わっていない席で増えるのは、記録を決めるたびの、起動より後に出来た記録の更新時刻の確かめだけ。

## 取らなかった形

- **起動の印を持つ記録のうち、いちばん新しく作られた物へ移る。** 元の会話へ戻った時に追えない。結び付け直した後で読み違いに気づいても、
  戻れない。更新時刻で比べれば、書かれている方が今の会話になる。
- **Codexのhook（SessionStart）で切り替えを受ける。** 全席が共有する`hooks.json`へ種類を足す事になる。連携元が頼っている登録を動かす。
- **席のprocessが開いているfileを見る。** Linuxでしか読めない。
- **完了待ちが席の登録を書く。** 完了待ちは読むだけ、という決まり（`observeAgentDone`）を崩す。持ち主の書き込みと競合する。

## 及ばない所

- 切り替えた後の最初のturnでは、合間の言葉（`interim_words`）は出ない。境界が、前の会話の記録の位置だから。次に送る時から出る。
- 切り替えた後の最初のturnの完了は、最長で3秒遅れて返る（見直しの間隔）。
- 入力欄で派生させた会話（`/fork`）と、前の会話へ戻る操作（`/resume`）で開いた、この起動より前の会話は追わない。今までどおり。
- 手で打った`/compact`・`/review`の途中に届いた文は、差し込みで返るが、Codexはその後の別のturnとして流す（下の「手で打った圧縮」）。

## 手で打った圧縮の途中に届いた文は、直さない

手で打った`/compact`の途中に届いた文を、Aitermは差し込み（`agent_steer`）で返す。Codexは「Messages to be submitted at end of turn」へ溜め、
圧縮の後に新しいturnとして流す。その完了は、誰も待っていない。

- 自動の圧縮（利用量が上限を超えた後のturnの頭で走る）は別で、実物で確かめた（2026-10-08）: 途中に届いた文は
  「Messages to be submitted after next tool call」へ入り、圧縮の後に同じturnへ入る。完了は1つ。直す所は無い。
- 手で打った圧縮と自動の圧縮は、途中の記録が同じ形（`task_started`の後に`token_count`だけ）で、記録からは見分けられない。
  見分けられるのは、文を送った後の画面の文言だけ。その文言はCodexの版で変わる。差し込みを新しいturnと読み違えると、
  動いているturnへの文に、来ない完了を待たせる事になる。
- 当たるのは、席の画面へ手で`/compact`を打った時だけ。文は失われず、回答は席の画面と`pty_read(agent_transcript:true)`で読める。

## 確かめ

- `test/codex-conversation-switch.test.mjs`: 新しい会話の記録を読む事と、元の会話へ書かれたら戻る事。別の起動の印・派生・
  `source`が`cli`でない会話・前に書かれた会話・起動より前に作られた会話・UUIDv7でないIDを拾わない事。書いている途中の記録を後で決める事。
  送信の道が席の登録を結び付け直す事。完了待ちが、送った後に出来た会話の完了を拾い、古い時刻の完了を数えず、席の登録を書かない事。
  読み位置なしの待ちが今より後の完了を待つ事。結び付けた会話が増えている間は、ほかの記録を見に行かない事。
- 実物（公式のCodex 0.160.1、画面つきの席、手元の偽のmodel。このコンテナ）: `/new`の後と`/clear`の後の文が新しいturnで返り、
  完了まで届き、`pty_read(agent_transcript:true)`が新しい会話の回答を返した。新しい会話で回答を流している間の2通目は差し込みで返り、
  完了は1つだった。直す前は、`/new`の後の完了待ちが時間切れだった。普通のturn、止めたturn、サービスの誤りで終わったturn、
  利用上限、回答を流している間の差し込み、手で打った圧縮、起こし直した席は、直す前と同じ返りだった。
