# ADR 0108: Codexのアプリが寝かせた会話を、会話を開かせて起こす

状態: 採用。ADR 0055の「Desktop独自機能は使わない」を、この1点（会話を開くリンク）だけ変える。

## 原因

Codexの親への配送は、本文を公式キュー（`thread/queue/add`）へ入れる。番の途中ならhookが同じ番へ入れ、止まっていれば公式キューが次の番にする（ADR 0055）。
止まっている会話で公式キューが動くのは、次の2つがそろう時だけだった（Codexの源`codex-rs/ext/queue/src/service.rs`、0.161.0と0.162.0-alpha.2で同じ）。

1. その会話が、動いているCodexのprocessに載っている（loaded）。見張りは10秒ごとに、載っている会話のキューだけを見る。
2. その会話の最後の番が、途中で止められていない（`turn_aborted`の`Interrupted`の後は、人が次の文を送るまで動かさない）。

Codexのアプリは、見ている接続が居なくなって動きの無い会話を60秒で下ろす（`thread_unload_delay_secs`。0.153.0までは30分）。
下ろされた会話のキューは、人がその会話を開くまで誰も見ない。

- 利用者の端末（macOS、Codex 0.162.0-alpha.2）の公式キューには、46通が16本の会話に残っていた（2026-10-09。一番古いのは9/27）。
  自動継続で乗り換えた後の古い会話あての分を除いても、番が普通に終わって寝た会話あてが20通あった。
  出どころは、通話の返信、決裁の答え、Aitermの子の回答。どれも共通パッケージ（aiterm-steer-delivery）の同じ入口を通る。
- 公式のCodexと手元の偽のmodelで再現した。見ている接続を外した会話は、ちょうど60.0秒で下ろされ、入れた文は35秒待っても番にならない。
  その会話を`thread/resume`した直後に番になる。番が普通に終わって載っている会話は、入れて9.9秒で番になる。
- 配送の目的は、返事が届いたら、待っていた会話が人の手を借りずに続きを進める事。寝ている会話が起きないのは、この目的を外している。

## 決めた事

1. **入れた後に、寝ていたら起こす見張りを別のprocessで起こす。** 作りは共通パッケージ（0.4.0の`submitCodexParentAnswer`と`codex-wake`）。
   Aitermの子の回答、`aiterm-parent-delivery codex submit`、パッケージのCLIを使う製品の配送が、同じ道を通る。
   配送を呼んだprocessがすぐ終わっても（命令）、見張りは最後まで走る。
2. **見張りは約15秒後にキューを見直す。** 文がもう無ければ（載っている会話が受け取った、hookが番の途中へ入れた）何もしない。
3. **文が残っていて、次の全部に当たる時だけ、OSの口で`codex://threads/<会話>`を開かせる。** アプリが会話を載せ、公式キューが番を始める。
   - アプリの会話である（公式の`thread/read`の`source`が`vscode`）。
   - 会話の記録の末尾で、最後の番が普通に終わっている（`task_complete`）。または番が1つも無い。
   macOSは`/usr/bin/open -g`（アプリを前面へ出さない）、Windowsは`cmd /c start`（人の画面のあるsessionの時だけ。サービスやsshのsessionから開いたリンクは、人の画面のアプリへ届かない）。
4. **起こさない会話。**
   - 番の途中（`task_started`で終わっている）: hookか、番の終わりの公式キューが渡す。
   - 最後の番が途中で止められている（`turn_aborted`）: 人が止めた会話と、ほかの製品が作業を別の会話へ移した後の古い会話。
     Codex自身が、人の次の文までキューを止めている。起こすと、止めた人やその製品の判断を覆す。
   - アプリの会話でない（CLIの席など）: 開いている席は載ったままで、当たらない。閉じた席をアプリで起こし直さない。
   - 会話の記録から番の状態を読めない: 起こさない側へ倒す。
5. **同じ会話へ続けて届いた時は、30秒の間は開き直さない。** 1通ごとに画面を切り替えない。
6. **結果を残して返す。** `~/.config/aiterm-mcp/codex-parent-hooks/wake/<配送ID>.json`に3日間。`aiterm-parent-delivery codex state`は、結果がある時だけ`wake`を付ける
   （`delivered`・`running`・`interrupted`・`not_app_thread`・`unknown_state`・`no_opener`・`open_failed`・`woken`・`opened_still_queued`）。
   受付の返り（`queued_submission_id`）と、今までの`state`・`hook`・`turn_id`・`queued`は変えない。
7. **見張りを起こすのは、macOSとWindowsだけ。** Linux（サーバー、コンテナ、Linuxのアプリ）では何も起こさない。止める時は`AITERM_STEER_CODEX_WAKE=0`。
   試験は`test/seat-env.mjs`でこれを立て、開発機やrunnerのアプリにリンクを開かせない。
8. 変えない物: 親の会話を別のprocessで載せない（`thread/resume`しない）事、modelや権限を渡さない事、旧中継の道、Claude Code・Cursor・Grokの親への配送。

## 取らなかった案

- **会話を寝かせない設定（`thread_unload_delay_secs`を延ばす）。** 公式の設定で、延ばせば載ったままになる（3600秒で確かめた）。
  会話1本ごとにMCPの組が常駐し続ける（利用者の端末で17本、約0.2GB）。アプリを起こし直した後の、まだ開いていない会話には効かない。
  利用者の端末の設定を製品が書き換える形になる。利用者は延ばさないと決めた（2026-10-09）。
- **配送のprocessが会話を載せて、番を回す（`thread/resume`）。** 画面が無くても動き、アプリが閉じていても届く。
  回している間、アプリはその会話を開けない（`already has an active writer`）。承認の問いに答える相手が居ない。アプリが起動時に足している道具が無い。
  番の長さだけ常駐するprocessが要る。ADR 0055の「親を別processで載せない」を崩す。
- **アプリの中の通信口（`~/.codex/ipc`）へ頼む。** 公開されていない取り決めで、版ごとに変わり得る。

## 弱さ

- 文が届いた時、アプリの画面がその会話へ切り替わる。別の会話で文を打っている最中だと、打ち先が替わる。
- 起きるまで、入れてから約15〜20秒かかる。
- キューは先頭から番になる。前から残っている文がある会話では、起きた時にそれらが先に番になる。
- 最後の番が途中で止められた会話あての文は、今までどおり、人が次の文を送るまで動かない。
- **Linuxのアプリは、まだ起こさない（確かめられていない）。** 利用者のLinux機（アプリ、Codex 0.162.0-alpha.2）で、利用者のsessionの環境から
  `xdg-open codex://threads/<会話>`を開かせても、会話は載らず、キューは動かなかった（2026-10-09）。その端末のアプリは、ログインの期限が切れていた
  （アプリの記録に`token_expired`）。リンクの口が効かないのか、ログインが切れていたせいかを、分けられていない。
  CodexがMCP serverへ渡す環境には`DISPLAY`も`WAYLAND_DISPLAY`も無いので、開くには利用者のsessionの環境を借りる口（`systemd-run --user`など）も要る。
  動く形を実物で確かめるまで、Linuxでは今までどおり、会話が開かれた時に届く。
- Windowsで、sshやサービスのsession（番号0）で動いているAitermが配送を引き取った時は、リンクを開けない（`wake`は`no_opener`）。
- リンクの形（`codex://threads/<id>`）と記録の行の形は、Codexの公開の取り決めではない。Codexの版が上がった時は、
  `tools`の再現（寝ている会話、開いた後の番）を流して確かめる。

## 確かめ

- 共通パッケージ: 単体（記録の末尾の読み、起こす・起こさないの振り分け、重ねて開かない、見張りの起こし方）と、公式のCodex＋偽のmodel
  （載っていない会話は開かせると番になる／載っている会話は開かない／止めた会話は起こさない）。
- 利用者の端末（macOS、Codex 0.162.0-alpha.2、実物のmodel）: 試しの会話を立てて番を終え、どこにも載っていない状態にして、
  `aiterm-parent-delivery codex submit`だけを呼ぶ。18.2秒後に2つ目の番が始まり、26.2秒後に合言葉の答え。`state`の`wake`は`woken`。
- 利用者の端末（Windows、同じ版）: 人の画面のあるsessionから同じ事を流す。18.6秒後に2つ目の番、38.7秒後に合言葉、`woken`。
  sshのsessionからは、リンクを開く口が無いと読む（`no_opener`）。
