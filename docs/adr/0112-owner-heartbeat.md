# ADR 0112: 配送の持ち主の生き死には、持ち主が付ける「生きている印」で読む（processを起こして確かめない）

状態: 採用。

## 原因

親への配送の回収（`recoverOrphans`）は、AitermのMCP process 1個につき2本（手元用と別端末用）、5秒おきに回る。
ほかの持ち主（MCP process）が、記録にある本人のまま生きているかを確かめるために、pidの有無（OSへ直接聞く）と、
60秒おきの開始時刻の照合（processを起こす。WindowsはPowerShell 7とWMI、ほかは`ps`）を使っていた。

- **回数が、processの数の掛け算で増える。** 照合を覚える時刻が持ち主ごとにずれるので、1本が1分に何回もprocessを起こす
  （5秒の刻みごとに、最大で12回）。MCP processが増えると、相手も、確かめる側も増える。
- **Windowsでは1回が重い。** PowerShell 7の起動に加えて、WMI（`Win32_Process`）は絞っても1回に0.1〜0.3秒かかり、
  WMIの側のprocess（wmiprvse）のCPUを使う。

2026-10-12、Windowsの端末（process 1312個、AitermのMCP process 23個）で、Aitermだけで20秒に78回のPowerShellが起きていた
（共通部品の待機の分と合わせて毎秒6.2回）。WMIの側のprocessがCPUを中央2.8コア使い、同じ端末で動かしていたゲームのコマ数が
半分になっていた。古い会話を止めてMCP processを23個から5個へ減らすと、20秒に26回、コマ数は元へ戻った。
会話を引き継ぐ仕組みを使うと、引き継がれた後の古い会話のprocessが長く残るので、MCP processは黙っていても増える。

## 決めた事

1. **持ち主は、自分の保存場所へ「生きている印」を付ける。** `active/<持ち主>/alive`（中身なし）の時刻を、15秒おきに書き直す。
   5秒おきの回収の先頭で書く（別のtimerを持たない）。
2. **印が新しい持ち主は、OSへ聞かずに生きていると読む。** 新しい＝60秒以内。pidを使い回した別のprocessは、この印を書かない。
   pidが無い持ち主は、今までどおり、すぐ「終了」と読む。
3. **印の無い持ち主（0.58.3までの版）と、印が古い持ち主だけ、今までどおり開始時刻で照合する。** 60秒に1回。
   誰かを照合する回には、覚えている持ち主も一緒に照合し直して、時刻を揃える（1本が起こすprocessは、1分に1回まで）。
4. **Windowsで1個のprocessの開始時刻を読む時は、WMIを使わない。** .NETのprocessの読み（`Process.StartTime`。OpenProcessとGetProcessTimes）を使う。
   1個1.5ミリ秒で、WMIの側のprocessを起こさない。値は今までと同じ文字列になる（WMIはマイクロ秒で切り捨てた値を返し、どちらも
   1ミリ秒で切り捨てて使う。実物の888個のprocessで食い違いは0）。権限が無くて読めないprocessだけ、WMIへ聞き直す。

### 印の決め方

- **60秒**は、書く間隔の4倍。持ち主のprocessは、同期の処理（子のprocessの終わりを待つ、など）で十数秒塞がる事がある。
- 持ち主が終わってpidが使い回された時、記録の引き取りは、印が古くなるまで最長60秒遅れる。今までの照合の間隔と同じ。
- 端末が眠った後は、全部の印が古く見える。その回だけ、全員を開始時刻で照合する（1本につき1回）。
- 時計が大きく動いた時も、印は「古い」と読まれるだけで、照合へ落ちる。印だけを見て記録を引き取る事は無い
  （引き取るのは、pidが無い時と、照合で別のprocessと分かった時だけ）。
- 名前は`.json`で終わらせない。回収は、保存場所の`.json`を配送の記録として引き取る。前の版も同じ絞り方をしている。

## 確かめ

- Windowsの実物で、AitermのMCP processを6個、同じ条件で150秒動かした（`tools/aiterm-probe/win/owner-poll-harness.mjs`）。
  0.58.3はPowerShellを80回（1分に32回）起こし、この版は0回。
- 前の版の持ち主が混ざる時の回数（覚えた時刻を揃える）と、印が止まった持ち主の引き取りは、試験で見ている。

## 変えなかった事

- `owner.json`の形、保存場所の名前、配送の記録と返り。前の版のMCP processは、この版の持ち主を今までどおり開始時刻で照合する
  （前の版のprocessが残っている間、その分のprocessの起動は続く）。
- pidの有無を5秒おきに見る事。OSへ直接聞くだけで、processを起こさない。
- 席の状態を読む時（`pty_observe`）の全processの一覧。これは呼ばれた時だけ取る。Windowsでは引数（CommandLine）が要るのでWMIを使う。
- Windowsのベル氏の案（processのhandleを1回開いて、終わるのを待つ）。nodeだけではOSのその口を呼べず、機械語の部品を足す事になる。
  印の形で回数が0になるので、入れていない。
