# ADR 0120: 席の設定替えは、送信と同じ行列に並ぶ

状態: 採用。

## 原因

`agent_configure`は、席の入力欄へharnessの命令（`/fast`・`/model`ほか）を打つ。打つ前に、入力待ちの確かめ（0.5秒おきに11回）と、
modelの一覧の問い合わせで数秒かかる。この間、設定替えは席ごとの送信の行列（ADR 0088）に並んでいなかった。

設定替えを頼んだ直後に同じ席へ`pty_send`が届くと、文が先に席へ入り、その番は替える前の設定で動く。設定替えは、番が終わるのを待ってから
命令を打つか、待ち切れずに断る。

実例（2026-10-13、BellTeamのCodexの席）: ファストを入れた3秒後に届いた1通が通常の速度で動き、その番の後に画面へ
「Service tier set to priority」が出た。手元の試験でも、切り替えが一覧を待っている間に送った文が、`/fast on`より先に席へ入った。

## 決めた事

- `agent_configure`は、席の控えを読む所から命令を打ち終えるまで、送信と同じ行列（同じprocessの待ち行列と、processをまたぐlock）を持つ。
  替えている間に届いた文は、替え終えてから振り分ける。先に送信が行列を持っている時は、設定替えが後ろに並ぶ。
- **番が動いている席では、行列を持ったまま番の終わりを待たない。** 順番が来た時に画面が番の最中を示していたら、何も打たずに行列を放し、
  0.5秒おいて並び直す（上限は今までの入力待ちと同じ30秒。越えたら今までと同じ「入力待ちではありません」）。
  待つ間も、その席への差し込みは今までどおり通る。
- 順番が来なかった時の断りは、送信と同じ`AGENT_SEND_BUSY`。末尾は「設定は変えていません。少し後で再度 agent_configure してください。」
  送信の断りの文（「文字列は送信していません。」）は変えない。
- 席の控えは、順番が来てから読む（前の送信が書いた分を、設定替えが古い控えで上書きしない）。

## 取らなかった形

- **呼び手に順番を任せる。** 呼び手が設定替えの返りを待ってから送れば起きないが、同じ席へ送る呼び手は1つとは限らない
  （親への配送、通話、別のprocessのAiterm）。席へ打つのはAitermなので、順番はAitermが持つ。
- **番が動いている間も行列を持って待つ。** 作りは短くなるが、通らない設定替えが、その席への差し込みを最長30秒止める。

## 残る事

- 画面が番の最中を示さないまま番が動いている席（Claude Codeの道具の最中、Codexが答えを流している間）は、今までどおり
  入力待ちの確かめ（11回続けて入力待ち）に任せる。この確かめは行列を持ったまま待つ。
- `agent_launch`の`fast: true`（起こした後の切り替え）は、起動の返りの前なので、行列には並べていない。

## 確かめ

- `test/fast-mode.test.mjs`: 設定替えが一覧を待っている間に送った文が、`/fast on`の後に席へ入る（直す前は先に入った）。
  番の最中の席への設定替えは、待つ間に届いた文が差し込みで通り、番が終わってから替わる。
- 公式のCodex 0.162.1の席（偽のmodelと一時の`CODEX_HOME`。番ごとの問い合わせの段を偽のmodelが控える）で、`agent_configure(fast: true)`を頼んだ
  3秒後に、返りを待たずに`pty_send`した。0.59.0: 送信は0.7秒で返り、その番は段なし（通常）で流れ、番の後に「Service tier set to priority」が出た。
  直した版: 送信は設定替えの返りの後に返り、その番は`priority`で流れ、「Service tier set to priority」は番の前に出た。
- 見ていない事: 本物のログインの席。別のprocessのAitermから届いた文（lockの作りは送信と同じ物を使う）。macOSとWindows。
