# 0127. 送信中のsource入力とmetadata競合を区別する

## 判断

native実行のsourceは検証済みlaunchであり、通常のincoming sendが同じsourceへ発行中でもそのlaunchは変わらない。sourceにslotがあることだけでoutgoing RPCを拒否せず、同世代・通常send・issued・対応recordが発行中の組だけをsourceの阻害条件から除く。targetのslot排他、source/targetの実世代検査、停止とRPC取消は各native作用前に維持する。unknown、作成・管理作用、孤立slot、世代不一致、source未確認は除外しない。slotやrecordの所有権は変えない。相互送信で循環待ちになるためincoming完了待ちも置かない。

agentの貼付けとEnterは間にawaitがある。各同期区間の前で既存metadata mutexの取得を非同期に待ち、取得後は同じ同期stack内で各gateを通す。transactionSyncはこの区間だけ同じmutexを使い、毎回stateを読み直して必要な発行checkpointをnative作用より先に保存する。区間はPromiseを返せず、await前にmutexを解放する。待つのはmutexだけで、native本体は一度だけ実行する。取得期限・破損・停止・世代交代等の不明を成功へ変えない。

BellTeamの管理close後のpromptなしagent_launchは、同じserving processのPID/開始識別子とSDK request IDへ結合する。deliveryを装った参照を作らず、prompt・portable fork・auto-name・remoteを許可しない。

## 根拠と試験

0.61.4では、貼付け後にsourceへの通常sendがissuedになるとEnter前のsource-slot検査がEXECUTION_UNCONFIRMEDを投げ、元送信をunknownへ固定した。実SDK＋実tmux＋偽Codex画面で同じエラー本文とslot状態を再現した。別writerがgraph lockを持つ場合も同期gateがEXECUTION_BUSYで拒否し、同じunknownへ変わった。修理後は貼付け・Enter各1回で完了する。

BellTeamの実障害6520c008には同世代sourceへのincoming280df032とHTTP時間窓の重なりがある。ただし失敗した瞬間のslot snapshot/throw位置は残らず、この1件の下位例外を一意に実証したものではない。lock単独の再現の本文はEXECUTION_BUSYで、実障害の一般UNCONFIRMEDと区別する。

execution-send-contentionは実SDK/実tmuxの競合、execution-native-admissionは相互送信・停止・交代・unknown保持・mutex排他・checkpoint先行を確認する。execution-management-closeは旧unknown不変・別席保持・管理close後のpromptなし実launchを通す。WindowsはPOSIX native graphをunsupportedのままとし、通常製品の回帰を3OS gateで確認する。
