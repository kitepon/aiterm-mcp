# Bound remote terminal adapter (C3 / C7 / C8)

Owner: Elegg. Consumers: BellTeam `terminals.connection` (Crust: binding, reachability, C8 setup), `execution` (Kiro, seat lifecycle), Throughline ingest (Rivalin, via execution). Contract sources: BellTeam PR 764 `modules/terminals/README.md` C3/C7/C8, PR 765 `modules/execution/remote-seat.md`. Targets: macOS, Linux (x64, arm64) and Windows (x64), Claude Code and Codex. A Windows terminal is reached through OpenSSH Server whose default shell is PowerShell 7 (`pwsh`), Windows PowerShell 5.1 or `cmd` (R21); only `TERMINAL_PLATFORM_UNSUPPORTED` for a system that is none of the three remains. Diagram: [remote-terminal.dot](remote-terminal.dot). Remote seats whose launch env contains credential names keep the existing rule: no resume recipe, so a hibernated one is relaunched fresh. It extends the existing [SSH relay](remote.dot); the per-call `remote` tool argument path is unchanged.

The key is readable only by UID1000 (no copy, no chmod), so every terminal SSH runs in a UID1000 Aiterm process: BellTeam's `execution-native-server` and the commands it runs from receipts.

## One launch path (Owner ruling 2026-11-09)

A terminal seat is launched by the same agent tool as a local seat. There is no second public entry for seats.

| Step | Public surface | What Aiterm does |
| --- | --- | --- |
| launch | `agent_launch`, `claude_agent`, `codex_agent`, `grok_agent` + `terminal: {ref, target: {host, user, port}, os?, trustRevision, credentialRevision}` + `cwd` | `terminal` is the value BellTeam terminals hands to execution (binding ref + its revisions), passed unchanged. Omitted = local, as before. Strict schema; a malformed value is `TERMINAL_INVALID`, never guessed, never a local fallback. `os` (`macos` / `linux` / `windows`) is an optional sibling of `target`, never inside it; BellTeam sends it only for linux and windows. Aiterm probes the terminal's real platform (R20) before the first terminal SSH call; a different declared `os` is `TERMINAL_OS_MISMATCH`, a system that is not macOS, Linux or Windows is `TERMINAL_PLATFORM_UNSUPPORTED`. `cwd` is required, in the terminal's native form: an absolute POSIX path starting with `/` on macOS and Linux, a drive-absolute `X:\...` path (backslashes; UNC, relative, drive-relative and `/` separators refused) on Windows; without `os` the form is checked against the probed platform before any session (`TERMINAL_INVALID`). Not combinable with `remote`. Harnesses: all five. `claude-code` needs terminal Aiterm 0.65.0, `codex-cli` 0.70.7, and `grok-cli`, `cursor-cli` and `antigravity-cli` 0.70.9 (`REMOTE_AITERM_TOO_OLD` from the cached `pty_list` version, before the private line is sent); all five go to the terminal's `agent_launch` the same way, and the R12 URL rewrite and header extraction apply unchanged. `TERMINAL_HARNESS_UNSUPPORTED` remains only for a harness name that is none of the five (unreachable through the tool schemas; kept as a guard). A CLI that is not logged in answers `AGENT_LAUNCH_NOT_STARTED: AGENT_AUTH_REQUIRED` (R18, below) |
| launch (inside) | `remote-terminal.ts` `terminalTarget` -> `remote.ts` | Binding and both revisions must match (T1). The launch call runs on its own SSH whose stdin first carries the private env line (R5): the values of `env_vars` (read from this process as for a local seat) and the header values of `mcp_config`, which are replaced in the config by `${AITERM_MCP_HEADER_n}`. Seat URLs under `/api/seat-mcp` must all be `http://127.0.0.1:<D>` with one D (else `SEAT_FORWARD_UNAVAILABLE` before any session); D is stored in the binding (`seat_ingress_port`) and the URLs get origin `http://127.0.0.1:<P>` (R12). harness `claude-code` calls the terminal's `claude_agent` (its `agent_launch` drops `mcp_config` before this release); `codex-cli` calls the terminal's `agent_launch` and needs the terminal's Aiterm >= 0.70.7 (`REMOTE_AITERM_TOO_OLD` before any private line), because older ones refuse or drop `append_system_prompt` / `mcp_config` for Codex. The shape of a Codex `mcp_config` is checked here first (after header extraction, so a `Bearer <secret>` header is already `${AITERM_MCP_HEADER_n}` and maps to `env_http_headers.Authorization`); a refusal is `AGENT_LAUNCH_NOT_STARTED` with `phase: "input"`. On success the session is bound (T2); `pty_list` `aiterm/seat_turns` rows for it come from the terminal's own `readSeatTurns` (Codex native tracking) exactly like a Claude terminal seat |
| later calls | `pty_send`, `pty_observe`, `pty_read`, `pty_key`, `claude_turn`, `pty_close`, execution `agent_stop`, … with `session_id` only | `registerRemoteAwareTool` finds the session in the terminal session map and forwards the same tool over a trusted SSH (`remote.ts` per-call path, R4). `pty_close` success unbinds. `agent_stop`: terminal `pty_observe`, then one `C-c` by `pty_key` only while `busy` (the plain terminal server has no `agent_stop`; the seat's own children on the terminal are not walked) |
| wait | receipt `wait_process` | `ssh` argv with the trusted options running the terminal's `aiterm-wait`; run as returned by a UID1000 process |
| transcript | `aiterm-transcript-read --session S [--cursor-session ID --offset N] [--max-bytes N]` | Local seat: reads locally. Bound session: runs the same reader on the terminal over trusted SSH. One JSON line `aiterm.transcript-read.v1` |
| seat MCP | reverse forward keeper (R12) | One Aiterm process per terminal holds `ssh -N -R 127.0.0.1:P:127.0.0.1:<D>` while bound sessions exist (lock in the state root); P and D are both read from the binding, never from the holder's environment; P is recorded and reused on reconnect. Every active Aiterm process checks every 60 s, so a forward whose holder exited is taken over within a minute |

`aiterm-remote-terminal` stays for terminals' binding/status/trust-confirm, the reachability check (`serve` open/close), C8 `remote_terminal_command` and the self-service steps before a terminal can open (`authorize-key`, `provision`; BellTeam PR 854 S2-S5). Its `remote_terminal_call` is no longer a seat launch path.

| ID | State | Content |
| --- | --- | --- |
| T1 | launch check | `terminal.ref` -> binding; `terminal.target` equals binding target; `trustRevision` equals current status. Key source: with `credential: {handle (UUID), revision (positive integer)}` (Mika's handle; `credentialRevision` must be absent; keyless bindings only) the key must already be loaded by `credential-load` for this ref with the same handle and revision (`CREDENTIAL_NOT_LOADED` / `CREDENTIAL_REVISION_STALE` otherwise); without it `credentialRevision` must equal the native key revision. A binding without a native key requires `credential` (`CREDENTIAL_REQUIRED`). `sudoCredential: {handle, revision}` (the terminal's sudo password) is only accepted and kept as a handle; nothing resolves or uses it until an explicit sudo operation exists. Later calls use the binding's current trust file with strict host checking, without revisions |
| T2 | terminal session map | `<state root>/terminal-seats.json` (0600) `{session_id: ref}`; written after a successful terminal launch, removed after `pty_close`. Survives an Aiterm restart; the seat itself lives on the terminal |
| T4 | platform and shell cache | in this process's memory, per binding ref (key of the trusted target): `macos` / `linux` / `windows` (or none when unknown) and the shell the terminal's sshd starts (`posix` / `powershell` / `cmd`; on Windows `cmd` when the probe expanded `%OS%`, else `powershell`). Filled by the first probe (R20), read by the later launches, command builds and `remote_terminal_open` of the same process; never written to disk. A different Aiterm process probes again |
| T3 | forward lock | `<state root>/terminal-forward-<ref>.lock` `{pid}`; taken when absent or its pid is gone. Every UID1000 Aiterm process with bound sessions checks it every 60 s, so a dead owner is replaced automatically |

Instructions and the MCP config are not secrets. They live in Aiterm's own 0700 launch state on the terminal (needed for exact resume) and are removed with the launch; nothing is written to the user's home config or the project. Secret values reach the remote only through R5, are held in the remote MCP process memory, enter the seat through the existing tmux session environment and the 0600 launch env file (deleted after sourcing), and stay in the existing 0600 resume recipe for exact resume, as local seats do today.

## Errors and exits (guards)

Each code is returned to terminals, which owns the retry. Every guard has an automatic exit through an authoritative revision.

| Code | Protects | Exit |
| --- | --- | --- |
| `HOST_TRUST_MISSING` | wrong target | `trust-confirm` with the Owner-confirmed fingerprint -> new revision -> reopen |
| `BINDING_UNKNOWN` / `TARGET_MISMATCH` | wrong target | terminals uses the registered binding for this terminal; a new `register` gives a new ref |
| `CREDENTIAL_REVISION_STALE` / `CREDENTIAL_UNAVAILABLE` | credential to wrong target | re-read status (key file restored or replaced) -> reopen |
| `CREDENTIAL_REQUIRED` (binding without native key, no `credential`) / `TERMINAL_INVALID` (both `credential` and `credentialRevision`) | credential to wrong target | the registry passes the terminal's credential handle |
| `CREDENTIAL_NOT_LOADED` (no live agent/metadata for the ref, or another handle) / `CREDENTIAL_REVISION_STALE` (loaded revision differs) | credential to wrong target | execution resolves the handle and runs `credential-load`, then launches again |
| `HOST_TRUST_STALE` (revision differs from the file) | wrong target / stale binding | terminals re-reads status, rebinds its revision -> reopen |
| `HOST_KEY_MISMATCH`, action "confirm the new host key" | wrong target | Owner confirms -> `trust-confirm` replaces the entry -> new revision -> reopen |
| `AUTH_FAILED` | credential to wrong target | key or authorized_keys corrected -> new revision -> reopen |
| `UNREACHABLE` | none (availability) | network/availability event -> reopen. Also `trust-confirm` when the scan returned no key line |
| `CONNECTION_REFUSED` | none (availability) | evidence that the TCP connection was refused (often the SSH server off: Remote Login on a Mac, sshd on Linux, the OpenSSH Server optional feature and its sshd service on Windows; not proven); the terminal's SSH starts accepting -> reopen |
| `PASSWORD_REJECTED` / `PASSWORD_AUTH_DISABLED` (`authorize-key`) | none | the caller asks the user again / the terminal offers no `password` method (keyboard-interactive is not used): the user adds the key another way. Never retried by Aiterm |
| `PASSWORD_INVALID` (`authorize-key`) | none | stdin was empty, not UTF-8, over 1023 bytes, or held NUL/CR/LF (ssh's askpass cannot carry them; nothing is stripped) |
| `AUTHORIZED_KEYS_WRITE_FAILED` (`authorize-key`) | existing state | `~/.ssh` or `authorized_keys` could not be created, chmodded or appended; the user fixes the folder -> run again |
| `FOLDER_NOT_PERMITTED` / `PATH_INVALID` (path ops) | none | the user grants access (privacy consent or permissions) / the caller passes an absolute path |
| `TERMINAL_OS_MISMATCH` (declared `os` differs from the probed platform; `remote_terminal_open` and launch) | wrong target | the Owner or BellTeam corrects the terminal's `os`, or registers the right machine -> reopen / launch again. Launch: not started (R18) |
| `TERMINAL_PLATFORM_UNSUPPORTED` (the system is neither macOS, Linux nor Windows, or the probe printed nothing recognisable) | none (feature not available) | use a macOS, Linux or Windows terminal. Launch: not started (R18) |
| `PROVISION_PLATFORM_UNSUPPORTED`, `PROVISION_BUSY`, `RUNTIME_DIR_UNAVAILABLE`, `RUNTIME_ARTIFACT_UNAVAILABLE`, `RUNTIME_DOWNLOAD_FAILED`, `RUNTIME_VERIFY_FAILED`, `RUNTIME_EXTRACT_FAILED`, `RUNTIME_SMOKE_FAILED`, `RUNTIME_ACTIVATE_FAILED` (`provision`) | existing state (the previous runtime stays usable) | not macOS, Linux x64/arm64 or Windows x64 / another provision is running (its pid ends, then the lock is taken over) / home not writable / this version's assets are not published yet (the release workflow uploads them) / network / checksum / disk / the new runtime failed its smoke / rename failed: run provision again |
| `REMOTE_AITERM_UNAVAILABLE` (POSIX `aiterm-mcp: command not found` / `No such file`; Windows: the `Get-Command` guard's `aiterm-mcp: command not found`, or the English cmd/PowerShell "is not recognized as ..." text that names an `aiterm-*` program) / `REMOTE_AITERM_TOO_OLD` (a Codex terminal launch needs 0.70.7; Windows path ops need 0.70.8) | none | `command('claude_*')` does not fix this; `provision --ref R` (or an Aiterm update on the terminal) -> reopen |
| `CWD_UNAVAILABLE` (launch result) | wrong folder | member folder revision -> fresh launch. No fallback to home, no later `cd` into another folder |
| `AGENT_LAUNCH_NOT_STARTED` (launch result; fresh native creation failed and its rollback was proven) | none (availability) | nothing remains under that session name; the caller launches again. The text keeps the cause (`native_reason=...` or the failed setup step) |
| `AGENT_LAUNCH_UNCONFIRMED` (launch result; fresh launch whose native identity could not be confirmed, absence not proven) | existing state (a native that may remain) | not projected as not-started. `pty_close` of that session name answers `closed` or `already_closed`; then launch again |
| `SESSION_EXISTS` (launch result; a live session already has that name) | existing state (the live seat) | the caller uses that seat or closes it with `pty_close`, then launches |
| `TERMINAL_INVALID` (malformed `terminal`, `os` outside macos/linux/windows, missing/relative `cwd`, a `cwd` in the other system's form such as `/x` on Windows or `C:\x` on macOS, `terminal` with `remote`) | wrong target | caller passes terminals' value unchanged with the project folder |
| `TERMINAL_HARNESS_UNSUPPORTED` | none | only for a harness that is none of the five (0.70.9); every real harness is routed |
| `AGENT_AUTH_REQUIRED` (inside `AGENT_LAUNCH_NOT_STARTED`; launch result) | none (the CLI has no login) | the Owner logs the CLI in on the terminal (`agent_auth` or the CLI's own login) -> launch again. Decided by the launch preflight where one exists: Claude (`claude auth status --json` says `loggedIn:false`), Cursor (`status` says not logged in), Antigravity (`models` says to sign in). Codex and Grok have no launch preflight (their status check runs only in `agent_auth`), so a logged-out Codex or Grok still stops at its own login screen. A status check that cannot be read is not this code (Claude `CLAUDE_AUTH_STATUS_UNCONFIRMED`, Antigravity `ANTIGRAVITY_AUTH_REQUIRED` with its message, Cursor's plain text) |
| `COMMAND_INVALID` / `COMMAND_UNSUPPORTED` / `CLI_INSTALL_UNSUPPORTED` / `CLI_NOT_INSTALLED` / `AUTH_STATUS_UNCONFIRMED` (`remote_terminal_command`) | none | bad op arguments / unknown op / no official installer known for that OS / the CLI is not on PATH nor in its installer's place / the status check printed something that is not a clear answer; the caller fixes the call, installs first, or asks the Owner |
| `SEAT_FORWARD_UNAVAILABLE` (terminal launch with seat MCP URLs: no forward port within 30 s, or seat URLs that are not `http://127.0.0.1:<D>` with one D) | wrong target (a seat MCP URL that reaches nothing, or the container's admin port) | the keeper keeps retrying; launch again / the caller passes one loopback seat port. Launches without seat URLs are not affected |
| `CONNECTION_LOST` (event `lost`, in-flight calls reject) | none | terminals reopens; the remote seat survives, the same `session_name` is observed again. Accepted `pty_send` is never replayed by the adapter |

### Not-started launch result (R18, BellTeam seatLaunch, Crust 2026-11-10)

Every code in the table below the launch path raises before any seat exists on the terminal: argument and binding checks (T1), the version probe and the launch call's SSH connect (no tool call was made), the seat forward wait, and the terminal's own pre-session refusals (`CWD_UNAVAILABLE`, Claude authentication preflight). The "not logged in" answer of the preflights is one code, `AGENT_AUTH_REQUIRED` (0.70.9), as `_meta["aiterm/launch_error"]` `{schema, harness, code, phase: "input", effect: "not_started", session_created: false, action}`; the text is `AGENT_LAUNCH_NOT_STARTED: AGENT_AUTH_REQUIRED: ...`. For Claude the old `structuredContent` (`CLAUDE_AUTH_NOT_AUTHENTICATED`) is kept beside it, and a terminal on 0.70.1 to 0.70.8 whose Claude answers only that structured code is mapped to the same `_meta`. Only those codes are projected as `effect: "not_started"`; everything else stays the plain error text, because the launch may have started. The projection is made by the server-side Aiterm only, so a terminal on any 0.67+ Aiterm gets it. One code is decided on the terminal: `AGENT_LAUNCH_NOT_STARTED`, raised by Aiterm 0.70.5+ after a native creation was rolled back and a complete session listing showed the name absent. An older terminal answers that failure as plain text (`AGENT_RESUME_UNCONFIRMED`), which is not projected.
