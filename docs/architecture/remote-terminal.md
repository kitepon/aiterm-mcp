# Bound remote terminal adapter (C3 / C7 / C8)

Owner: Elegg. Consumers: BellTeam `terminals.connection` (Crust: binding, reachability, C8 setup), `execution` (Kiro, seat lifecycle), Throughline ingest (Rivalin, via execution). Contract sources: BellTeam PR 764 `modules/terminals/README.md` C3/C7/C8, PR 765 `modules/execution/remote-seat.md`. Targets: macOS and Linux (x64, arm64), Claude Code. Windows terminals come in 0.70.8; this release recognises one and refuses it (`TERMINAL_PLATFORM_UNSUPPORTED`). Diagram: [remote-terminal.dot](remote-terminal.dot). Remote seats whose launch env contains credential names keep the existing rule: no resume recipe, so a hibernated one is relaunched fresh. It extends the existing [SSH relay](remote.dot); the per-call `remote` tool argument path is unchanged.

The key is readable only by UID1000 (no copy, no chmod), so every terminal SSH runs in a UID1000 Aiterm process: BellTeam's `execution-native-server` and the commands it runs from receipts.

## One launch path (Owner ruling 2026-11-09)

A terminal seat is launched by the same agent tool as a local seat. There is no second public entry for seats.

| Step | Public surface | What Aiterm does |
| --- | --- | --- |
| launch | `agent_launch`, `claude_agent`, `codex_agent`, `grok_agent` + `terminal: {ref, target: {host, user, port}, os?, trustRevision, credentialRevision}` + `cwd` | `terminal` is the value BellTeam terminals hands to execution (binding ref + its revisions), passed unchanged. Omitted = local, as before. Strict schema; a malformed value is `TERMINAL_INVALID`, never guessed, never a local fallback. `os` (`macos` / `linux` / `windows`) is an optional sibling of `target`, never inside it; BellTeam sends it only for linux and windows. Aiterm probes the terminal's real platform (R20) before the first terminal SSH call; a different declared `os` is `TERMINAL_OS_MISMATCH`, a Windows terminal is `TERMINAL_PLATFORM_UNSUPPORTED`. `cwd` is required (absolute POSIX path starting with `/` on macOS and Linux terminals, on that terminal). Not combinable with `remote`. Harnesses `claude-code` and (0.70.7) `codex-cli`; the other harnesses `TERMINAL_HARNESS_UNSUPPORTED` |
| launch (inside) | `remote-terminal.ts` `terminalTarget` -> `remote.ts` | Binding and both revisions must match (T1). The launch call runs on its own SSH whose stdin first carries the private env line (R5): the values of `env_vars` (read from this process as for a local seat) and the header values of `mcp_config`, which are replaced in the config by `${AITERM_MCP_HEADER_n}`. Seat URLs under `/api/seat-mcp` must all be `http://127.0.0.1:<D>` with one D (else `SEAT_FORWARD_UNAVAILABLE` before any session); D is stored in the binding (`seat_ingress_port`) and the URLs get origin `http://127.0.0.1:<P>` (R12). harness `claude-code` calls the terminal's `claude_agent` (its `agent_launch` drops `mcp_config` before this release); `codex-cli` calls the terminal's `agent_launch` and needs the terminal's Aiterm >= 0.70.7 (`REMOTE_AITERM_TOO_OLD` before any private line), because older ones refuse or drop `append_system_prompt` / `mcp_config` for Codex. The shape of a Codex `mcp_config` is checked here first (after header extraction, so a `Bearer <secret>` header is already `${AITERM_MCP_HEADER_n}` and maps to `env_http_headers.Authorization`); a refusal is `AGENT_LAUNCH_NOT_STARTED` with `phase: "input"`. On success the session is bound (T2); `pty_list` `aiterm/seat_turns` rows for it come from the terminal's own `readSeatTurns` (Codex native tracking) exactly like a Claude terminal seat |
| later calls | `pty_send`, `pty_observe`, `pty_read`, `pty_key`, `claude_turn`, `pty_close`, execution `agent_stop`, … with `session_id` only | `registerRemoteAwareTool` finds the session in the terminal session map and forwards the same tool over a trusted SSH (`remote.ts` per-call path, R4). `pty_close` success unbinds. `agent_stop`: terminal `pty_observe`, then one `C-c` by `pty_key` only while `busy` (the plain terminal server has no `agent_stop`; the seat's own children on the terminal are not walked) |
| wait | receipt `wait_process` | `ssh` argv with the trusted options running the terminal's `aiterm-wait`; run as returned by a UID1000 process |
| transcript | `aiterm-transcript-read --session S [--cursor-session ID --offset N] [--max-bytes N]` | Local seat: reads locally. Bound session: runs the same reader on the terminal over trusted SSH. One JSON line `aiterm.transcript-read.v1` |
| seat MCP | reverse forward keeper (R12) | One Aiterm process per terminal holds `ssh -N -R 127.0.0.1:P:127.0.0.1:<D>` while bound sessions exist (lock in the state root); P and D are both read from the binding, never from the holder's environment; P is recorded and reused on reconnect. Every active Aiterm process checks every 60 s, so a forward whose holder exited is taken over within a minute |

`aiterm-remote-terminal` stays for terminals' binding/status/trust-confirm, the reachability check (`serve` open/close), C8 `remote_terminal_command` and the self-service steps before a terminal can open (`authorize-key`, `provision`; BellTeam PR 854 S2-S5). Its `remote_terminal_call` is no longer a seat launch path.

| ID | State | Content |
| --- | --- | --- |
| T1 | launch check | `terminal.ref` -> binding; `terminal.target` equals binding target; `trustRevision` equals current status. Key source: with `credential: {handle (UUID), revision (positive integer)}` (Mika's handle; `credentialRevision` must be absent; keyless bindings only) the key must already be loaded by `credential-load` for this ref with the same handle and revision (`CREDENTIAL_NOT_LOADED` / `CREDENTIAL_REVISION_STALE` otherwise); without it `credentialRevision` must equal the native key revision. A binding without a native key requires `credential` (`CREDENTIAL_REQUIRED`). `sudoCredential: {handle, revision}` (the terminal's sudo password) is only accepted and kept as a handle; nothing resolves or uses it until an explicit sudo operation exists. Later calls use the binding's current trust file with strict host checking, without revisions |
| T2 | terminal session map | `<state root>/terminal-seats.json` (0600) `{session_id: ref}`; written after a successful terminal launch, removed after `pty_close`. Survives an Aiterm restart; the seat itself lives on the terminal |
| T4 | platform cache | in this process's memory, per binding ref (key of the trusted target): `macos` / `linux` / `windows` (or none when unknown). Filled by the first probe (R20), read by the later launches and by `remote_terminal_open` of the same process; never written to disk. A different Aiterm process probes again |
| T3 | forward lock | `<state root>/terminal-forward-<ref>.lock` `{pid}`; taken when absent or its pid is gone. Every UID1000 Aiterm process with bound sessions checks it every 60 s, so a dead owner is replaced automatically |

## Data flow

| ID | From -> to | Payload | Never carried |
| --- | --- | --- | --- |
| R1 | terminals -> `remote_terminal_status` | binding ref | paths, key |
| R2 | terminals -> `remote_terminal_open` (local stdio to UID1000) | ref, target, revisions, private env values | key/env in argv, other processes' env, files, logs |
| R3 | server -> private `ssh-agent` | `ssh-add <key file>` read by UID1000, or for a keyless binding the per-ref credential agent loaded by `credential-load` (R13); `serve` uses that agent's public key as its identity | key copy, key in any pipe |
| R4 | adapter -> `ssh` | `-F /dev/null`, explicit `-l/-p`, `-R` only on the forward keeper (R12), `StrictHostKeyChecking=yes`, `UserKnownHostsFile=<trust file>`, `GlobalKnownHostsFile=/dev/null`, `IdentityAgent=<socket>`, `IdentitiesOnly=yes` + agent public key, `BatchMode=yes` | user ssh_config aliases/options, other agent keys |
| R5 | adapter -> remote `aiterm-mcp` stdin | one private-env line, then MCP | values in argv or remote `process.env` |
| R6 | execution -> launch tool | today's launch args + `terminal` (terminals' value, unchanged) + `cwd` = projectRoot; later calls `session_id` only | secrets in any argument or prompt (values only by `env_vars` name) |
| R7 | remote Aiterm -> pane | `cd <cwd> && . <launch env file> && rm -f <file> && ... claude --append-system-prompt-file <file> --mcp-config <file>`; Codex: `... codex -c developer_instructions=<marker block + caller text> -c 'mcp_servers.NAME={url=..., bearer_token_env_var="ENV", env_http_headers={"H"="ENV"}}'` | env values (both); for Claude also instructions and MCP JSON in the PTY. A Codex seat's instructions and server URLs are in its argv (Codex has no file flag), so callers never put secrets there |
| R8 | Claude -> BellTeam MCP | `http://127.0.0.1:<P>/api/seat-mcp[/call-bridge]` on the terminal, through R12 to the container's loopback seat ingress (Molly; the port is the one in the URLs BellTeam passes, `src/remote-seat-port.mjs` RS01). Headers as the caller wrote them (literal or `${VAR}` expanded by Claude from env) | LAN listener, Owner/internal API |
| R12 | terminal sshd -> container | forward keeper `ssh -N -R 127.0.0.1:P:127.0.0.1:<D>` with `ExitOnForwardFailure=yes`. D = `seat_ingress_port` in the binding, written by the launch from the seat URLs; there is no environment variable and no default port: a binding without D builds no forward (its seats lose BellTeam MCP until relaunched, and the relaunch writes D). A launch with a different D writes the new D, clears P, and the keeper stops its ssh with the old D. First time P=0: `Allocated port P` from ssh stderr is recorded in the binding (`seat_forward_port`). Reconnects ask for the same P; refused 4 times in a row (the terminal still holds the old listener or another process took P) -> P=0 again and the new P is recorded (seats launched with the old P lose BellTeam MCP until relaunched). Each tunneled TCP connection dials the ingress fresh. The keeper restarts 15 s after its ssh exits while bound sessions exist; any active Aiterm process (60 s check) takes the lock over when its holder exits | token, LAN listener |
| R13 | execution (resolves Mika's handle in memory) -> `aiterm-remote-terminal credential-load --ref R --terminal-id ID --handle UUID --revision N --purpose ssh-key` via the seat process runner (UID1000) | raw OpenSSH private key bytes on stdin until EOF -> `ssh-add -` into the per-ref agent (`ssh-agent -D`, socket `/tmp/aiterm-ka-<uid>/<ref8>.sock` in a 0700 own dir, detached from the one-shot). Metadata `~/.config/aiterm/credentials/<ref>.json` (0600: handle, revision, terminal id, fingerprint, agent pid). One JSON receipt line `aiterm.credential-load.v1` {accepted, ref, terminal_id, handle, revision, fingerprint} or `aiterm.remote-binding-error.v1`. A new load replaces the agent's identities. Trusted SSH for that ref uses `IdentityAgent=<socket>`, `IdentityFile=none`. The agent and metadata are removed when no terminal seat or keeper of that ref remains and no launch is pending (2 min after the load), checked every 60 s by every active Aiterm process; after a host restart the agent is gone and calls answer `CREDENTIAL_NOT_LOADED` until execution loads again | key on disk, argv, env, PTY, logs, MCP arguments |
| R9 | `transcript.read` -> remote jsonl | session -> launch metadata -> `<claude home>/projects/<encoded cwd>/<id>.jsonl` from offset | - |
| R10 | `command(op)` -> remote shell | fixed script; output tail | arbitrary command, secret |
| R14 | caller (UID1000) -> `authorize-key --ref R` -> `ssh` password auth -> terminal `/bin/sh -s` | password: caller stdin -> this process's memory -> one connection on a 0600 socket in a private 0700 temp dir -> the `SSH_ASKPASS` helper (this CLI's `askpass` mode, which answers only a password prompt) -> ssh. Script on ssh stdin with the held public key (public) | password in argv, env, files, logs, PTY, error text; key-auth or keyboard-interactive attempts; a second attempt |
| R15 | `command(path_status / make_dir / list_dirs, path)` -> terminal `aiterm-remote-terminal path-status / make-dir / list-dirs --path-base64 B` (list-dirs without a path lists the home) | the path as base64 in the fixed command; one JSON line `aiterm.remote-path.v1` (`aiterm.remote-dirs.v1` for list-dirs) back | shell interpretation of the path |

One provision at a time (`.lock` with pid, taken over from a dead pid). Result line `AITERM_PROVISION <result> V <arch>` or `AITERM_PROVISION_ERROR <code>` | password, sudo, Homebrew/npm, the user's global packages, running tmux servers or seats (never stopped) |
| R17 | release -> `runtime.yml` (build jobs on `macos-latest` and `ubuntu-latest`, then one publish job) -> GitHub Release assets | after npm has the version: `scripts/build-macos-runtime.mjs` (pinned Node, tmux, libevent, utf8proc, jemalloc with sha256) builds both darwin arches, smokes the host arch, checks the other arch's binaries and their system-only libraries; `scripts/build-linux-runtime.mjs` builds linux-x64 and linux-arm64 with no compilation (the official Node linux tarball checked against its pinned sha256 and the published `SHASUMS256.txt`, the npm package with production dependencies, the same wrappers, no tmux) and smokes the x64 one against the runner's tmux. | R11 | adapter -> terminals | events + typed results | raw ssh stderr beyond the classified line |
| R18 | launch tool -> execution (terminal launch refused before the seat exists) | `isError` + `_meta["aiterm/launch_error"]` = `aiterm.agent-launch-error.v1` `{harness, code, phase: "terminal" (or "input" for a refusal decided from the arguments, below), effect: "not_started", session_created: false, action}` (not `structuredContent`: SDK clients that listed the tools validate it against the success outputSchema even on errors); `action` = a fixed plain Japanese sentence per code (`terminal-launch-error.ts`, at most 500 characters) for the Owner. A Claude authentication refusal from the terminal keeps its `structuredContent` and stays an error; its `_meta` copy keeps `phase: "authentication_preflight"`, `effect: "not_issued"` and adds `action`. Codes outside the table (a possibly started launch) get no structure. `AGENT_LAUNCH_NOT_STARTED` is the terminal's own answer (Aiterm 0.70.5+) for a fresh native creation that failed during setup and whose session name a complete listing then proved absent, with no dormant record; the terminal sends the code as text and the server projects it like the others. A local launch answers the same code with `phase: "native_create"`. A refusal decided from the arguments alone before anything exists (a caller field the harness cannot take, an inexpressible Codex `mcp_config`, a Codex stdio server of the same name) is `AGENT_LAUNCH_NOT_STARTED: <reason>` with `phase: "input"`, locally and on a terminal, for every harness; the server keeps a `_meta` the call already carries | native text, paths, host names, ssh stderr, key or secret values in `action` |
| R19 | a tool on a terminal session, or a terminal launch -> execution (refused) | `isError` + `_meta["aiterm/error_code"]` = `aiterm.error-code.v1` `{code}`: the leading symbolic code of the refusal text, whether the container raised it before SSH (T1, e.g. `CREDENTIAL_NOT_LOADED`; SSH classification) or the terminal's Aiterm answered it (`aiterm: CODE: ...`). A refusal without a leading code gets none. The code states the reason only; it claims nothing about the effect (R18 does that for launches) | text parsing by the caller; paths, stderr |
| R20 | launch tool or `remote_terminal_open` -> trusted ssh -> terminal default shell | the fixed one-line probe `echo aiterm-probe %OS% $PSHOME; uname -s`. cmd expands `%OS%` to `Windows_NT`, PowerShell expands `$PSHOME`, a POSIX shell prints the marker and then `Darwin` or `Linux` on its last line (a `uname` output of another system is unknown). Result `macos` / `linux` / `windows` / unknown, kept per ref (T4); `os` from the caller is compared with it; `remote_terminal_open` returns it as `platform` | the caller's `os` as proof (it is only compared), a guess when the probe printed nothing recognisable (unknown is refused, never assumed) |

Instructions and the MCP config are not secrets. They live in Aiterm's own 0700 launch state on the terminal (needed for exact resume) and are removed with the launch; nothing is written to the user's home config or the project. Secret values reach the remote only through R5, are held in the remote MCP process memory, enter the seat through the existing tmux session environment and the 0600 launch env file (deleted after sourcing), and stay in the existing 0600 resume recipe for exact resume, as local seats do today.

## Errors and exits (guards)

Each code is returned to terminals, which owns the retry. Every guard has an automatic exit through an authoritative revision.

| Code | Protects | Exit |
| --- | --- | --- |
| `HOST_TRUST_MISSING` | wrong target | `trust-confirm` with the Owner-confirmed fingerprint -> new revision -> reopen |
| `BINDING_UNKNOWN` / `TARGET_MISMATCH` | wrong target | terminals uses the registered binding for this terminal; a new `register` gives a new ref |
| `CREDENTIAL_REVISION_STALE` / `CREDENTIAL_UNAVAILABLE` | credential to wrong target | re-read status (key file restored or replaced) -> reopen |
| `CREDENTIAL_REQUIRED` (binding without native key, no `credential`) / `TERMINAL_INVALID` (both `credential` and `credentialRevision`) | credential to wrong target | the registry passes the terminal's credential handle |
| `CREDENTIAL_NOT_LOADED` (no live agent/metadata for the ref, or another handle) / `CREDENTIAL_REVISION_STALE` (loaded revision differs) | credential to wrong target | execution resolves the handle and runs `credential-load`, then launches again |
| `HOST_TRUST_STALE` (revision differs from the file) | wrong target / stale binding | terminals re-reads status, rebinds its revision -> reopen |
| `HOST_KEY_MISMATCH`, action "confirm the new host key" | wrong target | Owner confirms -> `trust-confirm` replaces the entry -> new revision -> reopen |
| `AUTH_FAILED` | credential to wrong target | key or authorized_keys corrected -> new revision -> reopen |
| `UNREACHABLE` | none (availability) | network/availability event -> reopen. Also `trust-confirm` when the scan returned no key line |
| `CONNECTION_REFUSED` | none (availability) | evidence that the TCP connection was refused (often the SSH server off: Remote Login on a Mac, sshd on Linux; not proven); the terminal's SSH starts accepting -> reopen |
| `PASSWORD_REJECTED` / `PASSWORD_AUTH_DISABLED` (`authorize-key`) | none | the caller asks the user again / the terminal offers no `password` method (keyboard-interactive is not used): the user adds the key another way. Never retried by Aiterm |
| `PASSWORD_INVALID` (`authorize-key`) | none | stdin was empty, not UTF-8, over 1023 bytes, or held NUL/CR/LF (ssh's askpass cannot carry them; nothing is stripped) |
| `AUTHORIZED_KEYS_WRITE_FAILED` (`authorize-key`) | existing state | `~/.ssh` or `authorized_keys` could not be created, chmodded or appended; the user fixes the folder -> run again |
| `FOLDER_NOT_PERMITTED` / `PATH_INVALID` (path ops) | none | the user grants access (privacy consent or permissions) / the caller passes an absolute path |
| `TERMINAL_OS_MISMATCH` (declared `os` differs from the probed platform; `remote_terminal_open` and launch) | wrong target | the Owner or BellTeam corrects the terminal's `os`, or registers the right machine -> reopen / launch again. Launch: not started (R18) |
| `TERMINAL_PLATFORM_UNSUPPORTED` (the probe says Windows, or the system is neither macOS, Linux nor Windows) | none (feature not available) | use a macOS or Linux terminal; Windows comes in 0.70.8. Launch: not started (R18) |
| `PROVISION_TMUX_MISSING` (`provision`, Linux terminal without `tmux` on the user's login PATH; raised before any download) | none | install tmux with the OS package manager (for example `apt install tmux`), then provision again |
| `PROVISION_PLATFORM_UNSUPPORTED`, `PROVISION_BUSY`, `RUNTIME_DIR_UNAVAILABLE`, `RUNTIME_ARTIFACT_UNAVAILABLE`, `RUNTIME_DOWNLOAD_FAILED`, `RUNTIME_VERIFY_FAILED`, `RUNTIME_EXTRACT_FAILED`, `RUNTIME_SMOKE_FAILED`, `RUNTIME_ACTIVATE_FAILED` (`provision`) | existing state (the previous runtime stays usable) | not macOS or Linux x64/arm64 / another provision is running (its pid ends, then the lock is taken over) / home not writable / this version's assets are not published yet (the release workflow uploads them) / network / checksum / disk / the new runtime failed its smoke / rename failed: run provision again |
| `REMOTE_AITERM_UNAVAILABLE` / `REMOTE_AITERM_TOO_OLD` (a Codex terminal launch needs 0.70.7) | none | `command('claude_*')` does not fix this; `provision --ref R` (or an Aiterm update on the terminal) -> reopen |
| `CWD_UNAVAILABLE` (launch result) | wrong folder | member folder revision -> fresh launch. No fallback to home, no later `cd` into another folder |
| `AGENT_LAUNCH_NOT_STARTED` (launch result; fresh native creation failed and its rollback was proven) | none (availability) | nothing remains under that session name; the caller launches again. The text keeps the cause (`native_reason=...` or the failed setup step) |
| `AGENT_LAUNCH_UNCONFIRMED` (launch result; fresh launch whose native identity could not be confirmed, absence not proven) | existing state (a native that may remain) | not projected as not-started. `pty_close` of that session name answers `closed` or `already_closed`; then launch again |
| `SESSION_EXISTS` (launch result; a live session already has that name) | existing state (the live seat) | the caller uses that seat or closes it with `pty_close`, then launches |
| `TERMINAL_INVALID` (malformed `terminal`, `os` outside macos/linux/windows, missing/relative `cwd`, `terminal` with `remote`) | wrong target | caller passes terminals' value unchanged with the project folder |
| `TERMINAL_HARNESS_UNSUPPORTED` | none | use `claude-code` or `codex-cli`; the other harnesses are added with the same arguments |
| `SEAT_FORWARD_UNAVAILABLE` (terminal launch with seat MCP URLs: no forward port within 30 s, or seat URLs that are not `http://127.0.0.1:<D>` with one D) | wrong target (a seat MCP URL that reaches nothing, or the container's admin port) | the keeper keeps retrying; launch again / the caller passes one loopback seat port. Launches without seat URLs are not affected |
| `CONNECTION_LOST` (event `lost`, in-flight calls reject) | none | terminals reopens; the remote seat survives, the same `session_name` is observed again. Accepted `pty_send` is never replayed by the adapter |

### Not-started launch result (R18, BellTeam seatLaunch, Crust 2026-11-10)

Every code in the table below the launch path raises before any seat exists on the terminal: argument and binding checks (T1), the version probe and the launch call's SSH connect (no tool call was made), the seat forward wait, and the terminal's own pre-session refusals (`CWD_UNAVAILABLE`, Claude authentication preflight). Only those codes are projected as `effect: "not_started"`; everything else stays the plain error text, because the launch may have started. The projection is made by the server-side Aiterm only, so a terminal on any 0.67+ Aiterm gets it. One code is decided on the terminal: `AGENT_LAUNCH_NOT_STARTED`, raised by Aiterm 0.70.5+ after a native creation was rolled back and a complete session listing showed the name absent. An older terminal answers that failure as plain text (`AGENT_RESUME_UNCONFIRMED`), which is not projected.
