# Benchmarks — aiterm vs. the built-in Bash tool

計測日: 2026-07-11 · 環境: macOS (darwin 25.5.0), Node, tmux · 対象リポ: aiterm-mcp 本体

この文書は README の「組み込みシェルツールとの使い分け / When to reach for it vs. the built-in shell」節の裏付けとなる実測ログをまとめたもの。README には要点だけを載せ、方法・全シナリオ・生の数値はここに残す。次に世代交代や競合比較をやるときは、まずここを見て測り直しの要否を判断する。

## 計測方法（フェアネスの担保）

- **トークン見積り = 文字数 ÷ 4**。これは aiterm 自身の推定式（`estimateTokens` = `Math.ceil(s.length / 4.0)`、[src/core.ts](../src/core.ts) 参照）。**同じ式を Bash 側の生出力バイト数にも適用**するので、比較は「実際にコンテキスト窓へ入るトークン量」で対等。
- **所要時間 = 実測 wall-clock**。各経路の前後を `python3 -c "import time; print(time.time())"` で挟んだ概算で、モデルの往復を含む。マイクロベンチではなく目安。
- **aiterm 側は温まった（既に開いている）セッションを使用**。一度きりの `pty_open` コストはセッション寿命に償却されるため除外。
- 全採取は本リポジトリ・当該セッションでの実出力。捏造・手書きの偽出力は無い。

## シナリオ別の結果

### 1. 軽い単発コマンド: `git log --oneline -5`

| | Bash ツール | aiterm |
|---|---|---|
| 呼び出し | 1 tool call | 2 tool call（`pty_send` + `pty_read`） |
| 所要 | ~6.7 秒 | ~12.8 秒 |

**勝者: Bash**。往復が少ない。`pty_send`/`pty_read` の分割はコマンドの重さに依存しない固定コスト。些細な読み取りは組み込みツールで済ませる。

### 2. 実テストスイート: `npm test`（ヒーローケース）

- スイート = 183 テスト。生ログ = 199 行 / 16,096 バイト。
- Bash: 全 199 行がコンテキストへ = 16096 / 4 = **~4,024 tok**。
- aiterm: head-30 + tail-20 に畳んで **~599 tok**。実メタ行:

  ```text
  [aiterm bench2: 51 行 / ~599 tok (raw 203 行 / ~3856 tok); 152 行 hidden] [is_complete=True via mark]
  ```

- **比率（コンテキストへ入る量）: 4024 / 599 = ~6.7× 少**。
- **要点: 判定が畳んでも生き残る**。残った tail に `ℹ tests 183 / ℹ pass 183 / ℹ fail 0` がそのまま載る＝削ったのはノイズで、必要な行ではない。
- 所要: Bash ~46 秒 / aiterm ~39 秒 ＝ ほぼ互角。長いコマンドでは往復オーバーヘッドが実行時間に埋もれる。

### 3. 大きなファイル列挙: `find node_modules -type f`（正直な引き分け）

- 3,777 ファイル / ~192 KB（生ダンプなら ~49k tok 相当）。
- Bash: 現行の Claude Code ハーネスは 192 KB をファイルへ**自動退避**し、先頭 ~2 KB のプレビューだけ見せる = **~500 tok**。生ダンプはしない。
- aiterm: **~456 tok**。実メタ行:

  ```text
  [aiterm bench2: 51 行 / ~456 tok (raw 3781 行 / ~50117 tok); 3731 行 hidden] [is_complete=True via mark]
  ```

- **比率: トークンはほぼ互角**（456 vs ~500）。aiterm の優位は量でなく質＝正確な行数と、あとから `line_range="A:B"` で任意範囲（先頭でも末尾でも）を取り出せること。ハーネスのプレビューは先頭のみで末尾が見えない。
- （もし Bash が生ダンプしていれば 50117/456 ≈ 110×。だが実際はしないので、その数字は主張しない。）

### 4. ソース横断 grep: `grep -rn "session" src/`

- 118 マッチ / 11,955 バイト。
- Bash: 全 118 行 = 11955 / 4 = **~2,989 tok**。
- aiterm（rtk reducer）: **~1,096 tok**。`118 matches in 5 files` ヘッダ付き。実メタ行:

  ```text
  [aiterm bench2: rtk:grep 適用 / ~1096 tok (raw ~2512 tok)] [is_complete=True via mark]
  ```

- **比率: 2989 / 1096 = ~2.7× 少**。
- **注意（lossy）**: 上の計測は 0.44.1 以前の reducer。0.45.0 から grep reducer は rtk 0.50.0 に合わせ、上限（全体 200 行・1 ファイル 25 行）に収まる間は出力をそのまま返す。上限を超えた時だけファイルごとにまとめ、長い行を検索語の周り ~80 字に切り、あふれを `+N more in <file>`／`+N more files` に畳む。大きな検索の全行を丸ごと読みたいときは組み込みツールを使う。
- 0.45.0 の再計測（2026-09-30、Linux、同じコマンドを当日の `src/` に対して）: 550 マッチ / 23 ファイル / 57,869 バイト。生 ~12,546 tok → rtk:grep ~4,286 tok（~2.9× 少）。

### 5. 反復の多い合成ログ: 同一警告行 × 200（合成＝ベストケース）

- Bash: 200 行の生出力 = **~4,754 tok**。
- aiterm: 反復圧縮で **~40 tok**（`〈×200〉` 表記）。
- **比率: ~119×**。ただし**合成**（同一行の反復）＝人工的なベストケース。README のヒーローには使わない。載せるなら「synthetic best case」と明示する。実ワークロードのヒーローはシナリオ2の 6.7×。

### 6. 呼び出しをまたぐ状態保持（%でなく、できる/できないの差）

`cd /tmp && export BENCH_VAR=hello123` を送り、**2 回目の別の呼び出し**で読み返す。

- Bash ツール: 2 回目で cwd はプロジェクト直下へリセットされ、環境変数は消える（`var=` 空）。Bash ツールの仕様＝cwd は呼び出し内では保つが呼び出し間でリセット、env は呼び出し間で保持しない。
- aiterm: 2 回目でも `cwd=/tmp var=hello123`＝両方保持（1 本の tmux セッション）。
- これは「できる/できない」の差。`cd`→env→build、`ssh` で一度入って認証済みセッションに 10 個コマンド、生きた REPL やエージェント TUI を 1 ターンずつ操作——どれも独立した Bash 呼び出しでは表現できない。速さでなく正しさの話。

## 結論（3点）

1. **軽い単発 → Bash が勝つ**（1 往復 vs 2）。些細な読み取りは組み込みツールへ。
2. **長い / 反復 / 大きな出力 → aiterm の削減が効く**。しかも判定は畳んでも残る（実スイートで 6.7×、183 pass / 0 fail 無傷）。
3. **呼び出しをまたぐ状態（cwd・env・ssh 認証・生きた REPL/エージェント TUI）→ aiterm だけが保持できる**。これは能力の差であって速さの差ではない。
