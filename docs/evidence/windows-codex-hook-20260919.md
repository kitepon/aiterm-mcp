# WindowsのCodex親hook修理の記録

## 観測と原因

2026-09-19、Codex Desktop同梱の`codex-cli 0.155.0-alpha.9.2`で確認した。
0.37.7のhookは公式APIで有効・承認済みだったが、実行中の回答取得記録が作られなかった。
CodexはPowerShell 7の`-Command`へhookコマンドを渡していた。
Aitermが生成した引用済みの実行パスには呼出し演算子`&`がなく、`-NoLogo`で構文エラーになった。

診断中には別の試験不備も見つかった。隔離環境が`PATHEXT`を継承せず、hook内では`.CPL`だけになっていた。
PowerShellはNodeを関連付けで起動し、入力待ちのNodeが6個残り、そのうち2個に窓があった。
所有する試験コマンドとPIDを確認して6個を終了した。試験環境へ`PATHEXT`を継承した後は残存しなかった。
根拠となる[PowerShellの実装](../../rag/sources/terminal-automation/powershell-native-command-20260919.md)も保存した。

## 修正と検証

Windowsのhook登録コマンドをPowerShellの呼出し演算子付きにした。回答取得・公式キュー・所有記録の処理は変えていない。
PowerShellからの標準入出力を、空白・引用符・日本語を含むパスで検証した。

公式バイナリの隔離試験は読取専用MCPの完了で`PostToolUse`を発火させる。
shellが承認ポリシーで拒否され、`Stop`だけが回答を受け取る場合を、実行途中の配送成功に数えない。
取得記録の`turn_id`とhookイベントの本文を照合し、最初のターンへの一度の配送を確認した。

関連試験33件は全件成功した。公式バイナリの7ケースには、実行途中・終了直前・終了後、
hook消失、終了との競合、利用者キューの保持、未承認の別hookを含む。
試験processは非表示で起動し、標準入出力のcloseまで待ってから一時領域を削除する。

これは隔離環境での記録であり、稼働中Desktopへの新版適用と再起動後の実配送を代替しない。
